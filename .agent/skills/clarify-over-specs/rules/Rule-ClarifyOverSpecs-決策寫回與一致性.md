# Rule 1 - 每輪 clarify 收斂後必須同步寫入正文與澄清紀錄

- Level: `MUST`
- 每輪 `/clarify` 取得已確認決策後，必須在同一輪內更新 `spec.md` 並存檔，不可只留在對話中。
- 若尚無 `## 澄清紀錄`，新增於 `## 假設` 之後；若已有，沿用結構追加。
- 每次 session 使用 `### Session YYYY-MM-DD`（日期為澄清當日）；每道採納的題目追加一行：`- Q: <總結之提問> → A: <最終答案>`。
- 允許新增的 heading 僅限 `## 澄清紀錄` 與 `### Session YYYY-MM-DD`；不得為了澄清而重排無關章節。

## Good Example

```md
## 澄清紀錄

### Session 2026-10-09

- Q: 缺少拍攝日期的照片是否只能存在一個「日期未知」相簿？ → A: 是，全系統唯一。

## 假設

- （已移除）待確認：未知日期相簿是否唯一 …
```

## Bad Example

- 這個例子是壞的，因為只在對話確認，spec 假設仍寫「待確認」。

# Rule 2 - 決策必須映射到正確的 spec 章節

- Level: `MUST`
- 依決策類型更新對應位置，且保持需求 ID 穩定；必要時新增 FR/NFR/BR 條目而非游离段落：
  - 可觀察行為、流程 → 相關 User Story 的 **FR** 或 **驗收情境**（Given/When/Then）
  - 跨故事政策、不變量 → **商業規則 BR** 或 **全域 FR**
  - 品質、效能、安全（產品可驗收）→ **NFR** 或 **成功標準 SC**
  - 實體、唯一性、關係 → **主要實體** 或相關 FR 敘述
  - 負向、異常、空狀態 → **邊界情況**
  - 待確認假設被拍板 → 更新正文並自 **假設** 刪除或改寫為已確認事實
  - 術語衝突 → 全文統一 canonical 用語，必要時一次註明 `(原稱 "X")`

## Good Example

- 這個例子是好的，因為決策同時更新 FR、邊界情況，並移除過時假設。

```md
- **FR-002**: …必須歸入**唯一**的「日期未知」相簿…
### 邊界情況
- 不得建立第二個「日期未知」相簿…
```

## Bad Example

- 這個例子是壞的，因為只在澄清紀錄寫 Q→A，FR 仍寫「待產品決定」。

# Rule 3 - 澄清後不得留下與新決策矛盾的舊文

- Level: `MUST`
- 若新答案使舊敘述無效，**替換**舊句，不要並列兩種互斥說法。
- 掃描同一 FR、假設、邊界、SC 是否仍含已解決的「待確認」「TBD」「可能」等語意；應一併修復。
- 新增內容須可驗證：避免把澄清結果寫成不可測的形容詞。

## Good Example

```md
（刪）假設：未知日期处理方式待確認。
（改）FR-002 已確認：…唯一「日期未知」相簿…
```

## Bad Example

```md
假設：未知日期處理待確認。
FR-002: 放入「日期未知」相簿。
澄清紀錄：Q: 是否唯一？ → A: 是。
```

# Rule 4 - 每次寫入後必須跑 validate_spec 與語意一致性檢查

- Level: `MUST`
- 每次更新 spec 後執行 `/specify` 的 `validate_spec.py`；失敗則修正後重跑。
- 語意檢查至少包含：
  - 澄清紀錄條數與本 session 採納題數一致（無重複 Q→A）
  - 更新章節中無與本次答案衝突的残留模糊描述
  - FR/NFR/BR/SC ID 仍唯一且全域參照有效
  - 術語在同一 spec 內一致
- 腳本通過不代表語意合格；兩者都通過才可進入下一輪 clarify 或 Phase 4。

## Good Example

- 寫回 → validate_spec 通過 → 對照 Rule 3 掃描「待確認」→ 再 delegate clarify。

## Bad Example

- 連續兩輪 clarify 後一次存檔，且未跑 validate_spec。
