# Rule 1 - 每筆 finding 必須標記為「已確認」「疑似」或「建議」三層之一

- Level: `MUST`
- **已確認（Confirmed）**：已人工追蹤程式碼實際執行路徑，或以可重現的測試／輸入驗證過缺陷確實存在，才可標記。
- **疑似（Suspected）**：僅由 Lint／SAST／DAST／SCA／AI 工具標記，尚未人工追蹤執行路徑或驗證觸發條件。
- **建議（Suggestion）**：屬可讀性、風格、架構優化等主觀改善意見，並非已證實的 Bug 或弱點。
- 三層缺一不可省略；報告中沒有標記層級的項目視為格式缺漏。

## Good Example

- 這個例子是好的，因為區分了已人工驗證與僅工具警告兩種狀態，並各自標記正確層級。

````text
F1 | 已確認 | 已追蹤 getUserOrder() 至 SQL 字串拼接，手動建構 payload 重現注入
F2 | 疑似 | Semgrep 標記 sql-injection 規則，尚未人工確認變數是否確實來自外部輸入
````

## Bad Example

- 這個例子是壞的，因為兩筆都只因工具警告就直接標成已確認，沒有人工驗證。

````text
F1 | 已確認 | SAST 工具標記 sql-injection
F2 | 已確認 | SAST 工具標記 sql-injection
````

# Rule 2 - 不得僅因自動化工具出現警告，就判定為確定的 Bug 或資安弱點

- Level: `MUST`
- 工具（Lint、SAST、DAST、SCA、AI）的輸出一律先視為「疑似」候選項，須經人工追蹤程式碼路徑、重現觸發條件，或以測試證明後，才可升級為「已確認」。
- AI 產出的 finding 若缺乏可追溯的檔案路徑與行號證據，不得標記為「已確認」，僅能列為「疑似」或直接標記為 AI 幻覺並剔除。
- 升級為「已確認」時，必須在「成因、觸發條件、可能影響」欄位寫出具體追蹤過程或重現步驟，不可只重複工具訊息原文。

## Good Example

- 這個例子是好的，因為升級為已確認前寫出了實際追蹤的輸入來源與資料流路徑。

````text
疑似 → 已確認：追蹤 req.query.id 未經檢核直接拼入 `SELECT * FROM orders WHERE id=` + id，
已於本機以 id=1 OR 1=1 重現回傳全表資料。
````

## Bad Example

- 這個例子是壞的，因為只複製 SAST 訊息原文就直接升級為已確認，沒有實際追蹤或重現。

````text
疑似 → 已確認：Semgrep 說這是 SQL Injection，所以確定是弱點。
````

# Rule 3 - 無法重現或資訊不足時，必須保留為疑似並說明待確認事項

- Level: `MUST`
- 若人工或 AI 嘗試追蹤後仍無法確定觸發條件、無法取得足夠上下文（如外部服務行為、執行期設定），必須維持「疑似」層級，並在報告中列出具體待確認事項（需要什麼資訊或由誰確認）。
- 不可因追蹤耗時或資訊不足，就擅自調降為「建議」或直接捨棄不報告。

## Good Example

- 這個例子是好的，因為清楚寫出維持疑似的原因與需要誰補充資訊。

````text
F3 | 疑似 | 無法確認第三方金流 callback 是否驗證簽章，需請負責該整合的開發者確認簽章驗證邏輯位置
````

## Bad Example

- 這個例子是壞的，因為追蹤不到就直接不列入報告。

````text
（追蹤金流 callback 簽章驗證時卡住，略過不報告）
````

# Rule 4 - 「建議」類項目不可使用資安或 Bug 的嚴重度字眼

- Level: `SHOULD`
- 「建議」層級的項目應使用「可讀性」「可維護性」「架構優化」等描述，不應使用「漏洞」「弱點」「Bug」等字眼，以免讀者誤判為已證實問題。
- 例外：若原為已確認問題但修正方式本身只是建議性質（如多種可行修法任選其一），可在建議修法欄位使用一般字眼，但問題本身的分類仍維持原本層級。

## Good Example

- 這個例子是好的，因為建議項目聚焦在可維護性措辭，沒有使用弱點字眼。

````text
S1 | 建議 | 函式 calculateTotal() 長達 150 行，建議拆分以提升可讀性與可測試性
````

## Bad Example

- 這個例子是壞的，因為把風格建議講成確定的資安弱點，誇大了嚴重性。

````text
S1 | 建議 | calculateTotal() 存在嚴重的安全漏洞，函式太長導致無法安全維護
````
