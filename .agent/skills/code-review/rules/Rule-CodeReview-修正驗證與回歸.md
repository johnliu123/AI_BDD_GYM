# Rule 1 - 結案前必須重新執行原先找出問題的分析方式，確認問題不再重現

- Level: `MUST`
- 修正後必須重跑當初發現該問題的工具或人工追蹤步驟（例如原本由 Semgrep 規則觸發，須重跑該規則；原本由人工追蹤發現，須重新走一次相同追蹤路徑或重現步驟）。
- 僅憑開發者口頭或 commit message 聲稱「已修正」，不足以結案；必須附上重新驗證的具體結果。

## Good Example

- 這個例子是好的，因為附上重跑同一工具規則的結果作為結案依據。

````text
F1 修正後重跑 Semgrep sql-injection-raw-query 規則：無命中。
已改用參數化查詢，手動以原重現步驟（id=1 OR 1=1）測試，回傳正常單筆結果。
````

## Bad Example

- 這個例子是壞的，因為只憑開發者聲稱已修正就結案，沒有任何重新驗證證據。

````text
開發者說已經修好了，結案。
````

# Rule 2 - 每個已確認問題修正後必須補上可重現原問題的回歸測試

- Level: `MUST`
- 修正已確認的 Bug 或資安弱點時，必須新增或更新至少一個測試案例，該測試在修正前應失敗、修正後應通過，用以防止未來回歸。
- 若該類問題不適合寫自動化測試（例如需要特定基礎設施才能重現），須在報告中說明原因，並記錄改用的替代驗證方式（如人工驗證腳本、檢查清單）。

## Good Example

- 這個例子是好的，因為新增的測試明確對應原問題且驗證修正前後行為差異。

````text
新增測試 test_order_lookup_blocks_sql_injection()：
傳入 id="1 OR 1=1"，驗證回傳結果筆數為 0（非整表），確認修正前此測試會失敗。
````

## Bad Example

- 這個例子是壞的，因為沒有新增任何測試，也沒有說明為何無法測試。

````text
已修正程式碼，未新增測試。
````

# Rule 3 - 確認修正未破壞既有功能，須重跑受影響範圍的既有測試與相關分析

- Level: `MUST`
- 修正後須重新執行受影響模組的既有測試套件（而非僅新增的回歸測試），並重跑該模組相關的 Lint／SAST／SCA 分析，確認沒有引入新的 finding。
- 若既有測試套件本身覆蓋率不足以涵蓋受影響範圍，須在報告中標註此限制，不可宣稱「無回歸風險」卻無對應測試佐證。

## Good Example

- 這個例子是好的，因為列出重跑範圍、結果，並誠實標註覆蓋率限制。

````text
重跑 orders 模組既有測試：42/42 通過。
重跑 Semgrep 全量掃描：無新增 finding。
限制：orders 模組的併發下單情境目前無自動化測試覆蓋，建議後續補充。
````

## Bad Example

- 這個例子是壞的，因為直接宣稱無回歸風險，卻沒有任何測試或分析佐證。

````text
修正後沒有回歸風險，可以合併。
````

# Rule 4 - 未完全修正或接受殘餘風險時，必須記錄風險接受理由與覆核時間

- Level: `MUST`
- 若問題因業務限制、技術限制或優先順序考量而未完全修正，不可直接標記為結案；須記錄：殘餘風險內容、接受風險的負責人、接受理由、下次覆核時間。
- 未記錄風險接受資訊前，該問題狀態應維持「待處理」或「部分修正」，不可標記為「已解決」。

## Good Example

- 這個例子是好的，因為完整記錄了殘餘風險、負責人、理由與覆核時間，而非直接結案。

````text
F5 狀態：部分修正（風險已接受）
殘餘風險：舊版 API 仍允許弱密碼，因相容性需求本季無法強制升級
風險接受人：王小明（技術主管）
理由：僅內部系統呼叫，對外已關閉該端點
覆核時間：2027-01-15 前重新評估是否可全面淘汰舊版 API
````

## Bad Example

- 這個例子是壞的，因為問題未完全修正卻直接標記已解決，沒有任何風險記錄。

````text
F5 狀態：已解決（因為時間不夠先這樣，之後再說）
````
