# Rule 1 - 衍生介面案例必須保留來源、需求 ID 與驗收面向

- Level: `MUST`
- 每個衍生 Example 必須標註來源 acceptance Feature 與 Example，並列入 package-level acceptance 覆蓋對照。
- 覆蓋對照必須列出來源 acceptance Example 對應的 `spec.md` 需求 ID（FR／NFR／BR／SC／User Story）；不得臆造 ID，也不得以 Scenario 名稱取代正式需求 ID。
- `spec.md` 中本次範圍內每個可驗收需求 ID 都必須對應至少一個 acceptance Example；無法對應時標記 unmapped 並交回 `/spec-by-example` 或 `/clarify`，不可由 `/dsl-refine` 靜默補造業務驗收或量測門檻。
- 覆蓋對照必須能由任一 acceptance Example 找到其所有衍生案例，也能由任一衍生案例回查來源。
- 衍生案例可以縮小到單一介面責任，但不得改變來源已確認的業務結果、遺漏必須維持不變的條件，或增加未經確認的業務行為。

## Good Example

- 案例本身標出來源，且對照表可追查其介面與模組。

```gherkin
  # Acceptance source: features/acceptance/下單.feature / Rule: 優惠結帳 / Example: 符合門檻後完成下單
  Example: 後端套用合格折扣碼後重算訂單金額
```

## Bad Example

- 下游案例沒有任何來源資訊，無法判斷它承接哪個 acceptance 行為。

```gherkin
  Example: 訂單摘要正確
```

# Rule 2 - 每個衍生 Rule 必須只驗證一個面向

- Level: `MUST`
- 每個 Rule 必須描述一個可獨立判定的業務或介面驗證契約。
- 若一個 Rule 同時要求不同結果、不同業務條件或不同責任面向，必須拆成多個 Rule；同一驗證面向下的相關 Then 可共同表達該契約。
- 下游 Feature 不得原樣保留 acceptance 的整段使用者 Journey 作為一條 Rule。

## Good Example

- Rule 聚焦於折扣碼未達門檻時，拒絕套用這一個結果。

```gherkin
Rule: 未達門檻的折扣碼必須被拒絕

  Example: 購物車金額低於折扣門檻
    Given 購物車商品金額未達折扣門檻
    When 顧客套用折扣碼
    Then 系統拒絕套用折扣碼
```

## Bad Example

- Rule 把拒絕折扣、付款成功、庫存扣減及寄送通知混成多個驗證面向。

```gherkin
Rule: 顧客完成優惠付款與商品出貨
```

# Rule 3 - 每個 Example 必須以一個 When 表達單一介面操作

- Level: `MUST`
- 每個 Example 必須採 3A 結構：可包含多個 Given，必須恰有一個 When step，並可包含多個 Then。
- 一個 When 只代表一次被測介面操作；後端以單次請求或命令為界。前端可將完成一個介面層級操作所需的複合 UI 互動收斂成一個業務可讀的 When。
- 若 acceptance Journey 包含多個被測操作，必須拆成不同的下游 Example；不可在同一 Example 串接多個 When 或多次操作。

## Good Example

- 多個 Given 安排商品與優惠；唯一 When 表達一次套用折扣碼操作；Then 驗證相關結果。

```gherkin
Example: 顧客套用折扣碼後看到正確折抵
  Given 結帳頁已有符合門檻的商品
  And 平台提供折扣碼「WELCOME100」
  When 顧客在結帳頁套用折扣碼「WELCOME100」
  Then 結帳頁顯示折扣碼已套用
  And 訂單摘要顯示正確折抵金額
```

## Bad Example

- 同一 Example 有多個 When，實際上測了不同操作與狀態轉換。

```gherkin
Example: 顧客完成優惠下單
  Given 顧客的購物車有商品
  When 顧客套用折扣碼
  And 顧客折抵點數
  When 顧客送出付款
  Then 訂單已付款
```

# Rule 4 - 遇到來源衝突或缺口必須停止受影響的衍生工作

- Level: `MUST`
- Acceptance Gherkin 是已確認業務行為的權威來源；system-analysis 產物用於判定介面責任與可觀察邊界，不得取代或靜默改寫 acceptance 行為。
- 若兩者衝突，或介面案例需要 acceptance 未定義的業務結果，必須停止受影響案例並交回 `/spec-by-example` 與 `/clarify` 收斂；不得自行新增預期、選擇其中一方或以註解掩蓋矛盾。
- 不受該缺口影響且可獨立判定的案例可繼續處理，但須在 coverage matrix 標記阻塞項及其來源。

## Good Example

- 有衝突的案例標記待上游決策，其他已有充分來源的案例仍可追溯交付。

```text
AC-01 → 前端/結帳/優惠碼套用.feature：已分配
AC-02 → 後端/訂單/付款失敗.feature：blocked，回交 /spec-by-example 與 /clarify
```

## Bad Example

- 為了完成下游測試，未經確認就替 acceptance 補上付款失敗後的業務結果。

```gherkin
Then 系統自動取消訂單並退還點數
```
