# Rule 1 - Discover 飽和度必須依專案規模分級

- Level: `MUST`
- 專案規模定義見 `references/principles.md` Project-Aware 章節。
- **輕量**：有明確規格或既有資料佐證即可；可不做正式訪談。
- **標準**：約 3–5 次訪談或等量支援單/行為資料，且開始出現**重複模式**。
- **完整**：涵蓋主要 segment；質化達飽和（新訪談不再出新主題，常見約 12–20 次，依領域調整）；並有量化交叉驗證。
- 未達該級門檻時不得宣稱 Discover Exit 達成，除非使用者知情接受較弱證據（見 `Rule-DoubleDiamond-例外與退回.md`）。

## Good Example

- 這個例子是好的，因為標準規模下樣本與重複模式都對照分級表。

````text
標準規模 SaaS 留存問題 → 4 次訪談 + CRM → 第 3 次起主題重複 → 可評估 Discover Exit。
````

## Bad Example

- 這個例子是壞的，因為完整規模專案只用一次訪談就宣稱飽和。

````text
策略級新產品 → 1 次朋友訪談 → 宣稱「已充分理解使用者」。
````

# Rule 2 - Develop 進 Deliver 必須滿足統一驗證門檻

- Level: `MUST`
- **不分規模，一律必須**：
  - 至少 **1 輪真實使用者測試**（不可僅內部評審或 AI 自評）。
  - Feasibility 由懂技術/營運者或既有技術限制文件確認。
  - Viability（資源、商業意義）已確認。
- **依規模的原型數量**：
  - **輕量**：≥ **1** 個概念完成原型並完成上述 1 輪使用者測試。
  - **標準 / 完整**：≥ **2** 個**差異化**概念各自至少 1 輪使用者測試（避免只做一個就收斂）。
- 證據不足時須標註 **證據等級：弱／中／強** 與 **尚待驗證假設**，不得宣稱「已驗證」。

## Good Example

- 這個例子是好的，因為標準規模下兩概念都有使用者測試且 F/V 有出處。

````text
概念 A/B 各 5 人可用性測試 → 工程師確認 API 可行 → PM 確認 ROI → 證據等級：強。
````

## Bad Example

- 這個例子是壞的，因為標準規模只測一個概念且無 F/V。

````text
只做一個 wireframe、只給同事看 → 直接進 Deliver。
````

# Rule 3 - 證據等級必須在產出中明示

- Level: `SHOULD`
- 當證據弱於該規模預設門檻但使用者選擇前進時，產出須包含：
  - 證據等級（弱/中/強）
  - 尚未驗證的假設清單
  - 建議補驗證的時機與方法
- 不可把「草稿」「假設」「待確認」偽裝成已 sign-off 的定案。

## Good Example

- 這個例子是好的，因為弱證據前進時風險透明。

````text
證據等級：弱；假設：「取消主因是價值感不足」；建議上線後 2 週補 5 次訪談。
````

## Bad Example

- 這個例子是壞的，因為只有桌面研究卻寫「已驗證使用者需求」。

````text
競品分析 + 推測 → 文件標題「Validated Problem Statement」。
````
