# Rule 1 - 行為變更預設使用 TDD，例外必須明確說出理由

- Level: `MUST`
- 只要任務會新增行為、修正 bug、改變既有輸出、補 edge case，或要求用測試證明結果，就預設走 TDD。
- 若任務屬於 throwaway prototype、純設定調整、純文件、生成檔、或主要驗證必須依賴昂貴人工檢查，才可不走完整 TDD；此時必須先向使用者說明原因與替代驗證方式。
- 不可因為「趕時間」「應該很簡單」或「先寫再補測試比較快」而跳過紅燈。

## Good Example

```md
任務：修正折扣計算在滿額邊界少算 1 元的 bug

決策：
- 這是既有行為修正，必須先寫重現 bug 的 failing test

任務：調整 README 內的安裝說明

決策：
- 這不是行為變更，不走 TDD
- 替代驗證：檢查指令與目錄路徑是否與現況一致
```

## Bad Example

```md
任務：新增重試機制

決策：
- 先把程式寫完，之後如果有空再補測試
- 理由：這功能看起來很直覺
```

# Rule 2 - 驗證若太慢或 oracle 不清楚，先縮小 seam 與切片

- Level: `SHOULD`
- 若完整驗證很慢、很脆弱，或需求還沒有清楚到能寫出可執行 oracle，應先縮小到較小的 public seam 或更薄的 vertical slice，再進入 RED。
- 若縮小後仍無法得到可信紅燈，應停下來補對齊需求或改變驗證策略，不要用模糊斷言假裝自己在做 TDD。
- TDD 的前提是「能用測試證明」，不是「能寫一段長得像測試的程式」。

## Good Example

```md
觀察：
- 端到端流程要 8 分鐘，且需求只先確定輸入驗證規則

調整：
- 先把 seam 縮到 `validateSignupInput()`
- 先測 email 與密碼格式規則，不先碰整段註冊流程
```

## Bad Example

```md
觀察：
- 使用者只說「讓 dashboard 感覺更快」

做法：
- 直接寫 `expect(pageFeelsFast).toBe(true)`
- 不先拆成可量測的行為或性能門檻
```

# Rule 3 - 沒看過正確紅燈，就不得寫 production code

- Level: `MUST`
- 每一輪都必須先寫測試、親自執行、看見它因為「尚未實作的行為」而失敗，之後才能進入 production code。
- 若先偷寫了 production code，即使只是「先當參考」，也應刪掉後重新從紅燈開始。
- 沒看到紅燈就進入綠燈，等同沒有證明測試真的會抓到缺口。

## Good Example

```md
順序：
1. 寫一個驗證 `retry 只重試 3 次` 的測試
2. 執行測試，看到因為尚未有 retry 邏輯而失敗
3. 才開始補最小實作
```

## Bad Example

```md
順序：
1. 先把 retry 邏輯大致寫完
2. 再補測試確認它現在是綠的
3. 說自己有遵守 TDD
```

# Rule 4 - 一次只做一個 vertical slice，不做 horizontal slicing

- Level: `MUST`
- 每一輪只允許一個 seam、一個主要行為、一個測試、一個最小實作。
- 不可先把所有測試一次鋪完，再回頭補所有實作；那會讓測試驗證想像中的設計，而不是與實作互相校正。
- 每個 slice 都應像 tracer bullet：用最小可驗證行為推進設計，而不是先承諾整個架構。

## Good Example

```md
切片順序：
1. 先讓 `createUser()` 能建立最簡單的有效使用者
2. 下一輪再處理重複 email
3. 再下一輪才處理歡迎信
```

## Bad Example

```md
切片順序：
1. 先把建立使用者、重複 email、歡迎信、權限檢查的所有測試一次寫完
2. 再開始一次補齊全部 production code
```

# Rule 5 - GREEN 只寫剛好通過本輪紅燈的最小實作

- Level: `MUST`
- GREEN 的目標是把目前紅燈轉綠，不是順便把下一輪也做完。
- 不可預作未來 edge case、先塞抽象層、先加還沒被測到的條件分支，或把需求尚未確認的行為一起實作。
- 若發現自己正在寫「反正等等大概也會需要」，應先停手，刪回到本輪測試真正要求的最小版本。

## Good Example

```md
當前紅燈：
- 有效購物車可成功 checkout

GREEN：
- 只補成功結帳所需最小流程
- 不先處理過期優惠券、庫存不足、寄信通知
```

## Bad Example

```md
當前紅燈：
- 有效購物車可成功 checkout

GREEN：
- 一次加入折扣規則、庫存同步、通知、補償交易、分析事件
```

# Rule 6 - refactor 只能在綠燈後進行，且不得擴大需求範圍

- Level: `SHOULD`
- 只有在目前相關測試已全部綠燈時，才做命名調整、重複消除、小幅抽取等 behavior-preserving cleanup。
- 若整理已牽涉新設計取捨、跨模組重構或新需求切片，應停止並回報使用者，而不是把 refactor 當成偷偷擴 scope 的藉口。
- refactor 完成後必須重新執行受影響測試，確認仍然維持綠燈。

## Good Example

```md
綠燈後整理：
- 重新命名變數
- 抽出重複的純函式
- 刪除本輪產生的重複判斷
- 再跑一次相關測試
```

## Bad Example

```md
綠燈後整理：
- 順手把整個 module 改成事件驅動架構
- 一起換資料庫 schema
- 再補兩個還沒談好的需求
```
