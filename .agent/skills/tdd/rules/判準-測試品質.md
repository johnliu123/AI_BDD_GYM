> 本檔合併原「好測試與壞測試判準」「測試結構與3A註解格式」「Mock-僅限系統邊界」三份規則。Good/Bad Example 僅示範規則的正反應用，判斷依據見各規則本文，不逐例重複說明理由。

# Rule 1 - 好測試描述使用者或呼叫者在乎的行為

- Level: `MUST`
- 測試名稱與斷言都應描述 `WHAT`，不是 `HOW`。
- 好測試應透過 public seam 驗證可觀測行為，讓內部實作就算重構，測試也仍然成立。
- 預期值必須來自獨立 oracle，例如已知字面值、明確規格、人工算例或對外契約，而不是跟著實作一起重算。

## Good Example

```md
測試名稱：
- `使用有效購物車可完成結帳`

斷言：
- `checkout(cart, paymentMethod)` 回傳 `status = confirmed`

另一個例子：
- `calculateTotal([{ price: 10 }, { price: 5 }]) === 15`
```

## Bad Example

```md
測試名稱：
- `checkout 會呼叫 paymentService.process`

斷言：
- 驗證 internal collaborator 的 call count 與參數

另一個例子：
- `expected = items.reduce(...)`
- `expect(calculateTotal(items)).toBe(expected)`
```

# Rule 2 - implementation-coupled 測試必須視為錯誤方向

- Level: `MUST`
- 出現下列訊號時，應判定測試過度耦合實作：mock 自家 internal collaborator、直接測 private method、依賴 call order / call count、或只要重構就會壞但行為其實沒變。
- 一旦發現 implementation-coupled 測試，應先回到 seam 與 oracle 重新設計測試，不可硬著頭皮沿用。
- 若測試的重點只能用「因為我知道它裡面怎麼做」來解釋，這通常就是錯的。

## Good Example

```md
需求：
- 建立使用者後應可被讀回

測試：
- `user = createUser({ name: "Alice" })`
- `retrieved = getUser(user.id)`
- `expect(retrieved.name).toBe("Alice")`
```

## Bad Example

```md
需求：
- 建立使用者後應可被讀回

測試：
- mock `UserRepository.save`
- 驗證 `save` 被呼叫一次
- 或直接測 `UserService._normalizePayload()`
```

# Rule 3 - tautological 測試不能當作有效證明

- Level: `MUST`
- 若 expected value 是用與實作相同的運算、分支或映射重新算出來，測試就會「天生同意」實作，不能算有效證明。
- 預期值必須能在不相信當前實作的前提下成立。
- 若真的找不到獨立 oracle，先回頭釐清需求、舉例或拆更小的案例，不要硬寫 tautological test。

## Good Example

```md
案例：
- `calculateTotal([{ price: 10 }, { price: 5 }]) === 15`
- `retryCount` 上限為 `3`
- 狀態轉移後應回傳 `archived`
```

## Bad Example

```md
案例：
- `expected = items.reduce((sum, i) => sum + i.price, 0)`
- `expected = normalize(input).trim().toLowerCase()`
- 再拿這些 expected 去驗證同一個邏輯的函式
```

# Rule 4 - 一輪只寫一個可讀、可診斷的測試

- Level: `SHOULD`
- 每個 test 預設只承擔一個主要行為斷言，讓紅燈原因與綠燈意義保持清楚。
- 若同一個測試同時涵蓋成功路徑、錯誤路徑、邊界值與多個條件分支，通常表示應切成多個 vertical slices。
- 測試內容應讓人一眼看出 Arrange、Act、Assert 的結構；撰寫、修改或重寫真實測試檔時，依 Rule 5–7 使用一致的 3A 註解格式。

## Good Example

```md
測試：
- 建立一個有效購物車
- 執行 `checkout`
- 只斷言結果是 `confirmed`
```

## Bad Example

```md
測試：
- 同時驗證成功結帳、付款失敗、優惠券過期、庫存不足、寄信通知
- 任何一處失敗都會讓整個測試一起紅
```

# Rule 5 - 撰寫或重寫測試時以 3A 註解格式組織段落

- Level: `MUST`
- 當在真實測試檔中新增、修改或重寫單一測試時，應以 `# Arrange`、`# Act`、`# Assert` 作為段落註解，讓準備、執行與驗證邊界清楚可讀。
- 3A 註解的目的，是把測試中的 setup、觸發行為與結果驗證切開，讓讀者能快速看出目前測的是什麼行為。
- 不可把多個無關目的的程式碼混在同一段，讓段落名稱失去辨識價值。

## Good Example

```py
def test_addition():
    # Arrange
    calc = Calculator()

    # Act
    calc.press("2")
    calc.press("+")
    calc.press("3")
    calc.press("=")

    # Assert
    assert calc.display == "5"
```

## Bad Example

```py
def test_addition():
    calc = Calculator()
    calc.press("2")
    calc.press("+")
    calc.press("3")
    calc.press("=")
    assert calc.display == "5"
```

# Rule 6 - 每個 3A 段落只放對應性質的程式碼

- Level: `MUST`
- `Arrange` 只放建立測試物件、準備資料、設定前置狀態等程式碼。
- `Act` 只放本次要觀察的行為觸發；若需要多行呼叫才能構成同一次行為，可以集中放在同一段。
- `Assert` 只放驗證結果的 assertion，避免把新的狀態準備或額外行為夾帶進來。
- 不可在 `Assert` 段落才補前置資料，也不可在 `Arrange` 段落先偷跑主要行為，否則 3A 只剩表面註解。

## Good Example

```py
def test_clear_resets_display():
    # Arrange
    calc = Calculator()
    calc.press("9")

    # Act
    calc.press("C")

    # Assert
    assert calc.display == "0"
```

## Bad Example

```py
def test_clear_resets_display():
    # Arrange
    calc = Calculator()
    calc.press("9")
    calc.press("C")

    # Assert
    assert calc.display == "0"
```

# Rule 7 - 不存在的段落應直接省略，不保留空 3A 註解

- Level: `MUST`
- 若某個測試不存在對應段落，應直接省略該註解，而不是留下空的 `# Arrange`、`# Act` 或 `# Assert`。
- 例如只有建構物件後直接驗證初始狀態的測試，可以只有 `Arrange` 與 `Assert`；像 smoke test 這種只有單一 assertion 的測試，可以只保留 `Assert`。
- 省略不存在的段落，是為了讓註解仍然反映真實結構，而不是機械地把 3A 填滿。

## Good Example

```py
def test_new_calculator_shows_zero():
    # Arrange
    calc = Calculator()

    # Assert
    assert calc.display == "0"
```

## Bad Example

```py
def test_new_calculator_shows_zero():
    # Arrange
    calc = Calculator()

    # Act

    # Assert
    assert calc.display == "0"
```

# Rule 8 - 只 mock 系統邊界，不 mock 自己控制的內部模組

- Level: `MUST`
- mock 的目標應限於外部 API、第三方服務、時間、亂數、部分檔案系統或難以穩定控制的真正系統邊界。
- 不可 mock 自家 class、internal collaborator、repository wrapper、service-to-service 協作細節，或任何你其實可以透過真實介面觀察的東西。
- 若目前只能靠 mock internal collaborator 才寫得出測試，先回頭檢查 seam 是否選錯（見 Rule 2）。

## Good Example

```md
可以 mock：
- 第三方金流 client
- 系統時間 `Date.now()`
- 亂數來源
- 難以穩定重現的外部檔案儲存服務
```

## Bad Example

```md
不應 mock：
- `UserService` 內部呼叫的 `UserRepository`
- `CheckoutService` 內部 helper
- 自己專案裡可直接執行的 domain module
```

# Rule 9 - 優先讓邊界介面本身可 mock，而不是在測試內寫條件式假物件

- Level: `SHOULD`
- 面對系統邊界時，應透過 dependency injection 或明確 adapter 介面傳入依賴，而不是在 production code 內直接 new client。
- 若一個 mock 需要靠大量 `if endpoint == ...` 或 `if action == ...` 才能運作，通常表示邊界介面過於籠統，應先拆成更具體的操作。
- mock setup 應讓讀者清楚知道該測試碰了哪個外部能力，而不是讓一個超大 mock 吞掉所有情境。

## Good Example

```md
較佳設計：
- `processPayment(order, paymentClient)`
- `api.getUser(id)`
- `api.createOrder(data)`

效果：
- 每個測試只 mock 自己碰到的外部操作
- 不需要在 mock 裡寫一堆條件分支
```

## Bad Example

```md
較差設計：
- `processPayment(order)` 內部自己 new `StripeClient`
- `api.fetch(endpoint, options)` 承接所有事情

後果：
- 測試要靠 endpoint 判斷分支
- 很難看出這輪真正驗證的是哪個能力
```

# Rule 10 - 能用真實但可控的替身時，優先用真實替身而非過度 mock

- Level: `SHOULD`
- 若可以使用 test DB、本機 memory fake、sandbox API 或其他可控替身達到更高真實度，應優先考慮，而不是預設所有邊界都 mock 掉。
- 選擇 mock 的理由應是為了隔離不可控邊界，而不是為了讓測試看起來比較容易寫。
- 若 mock 讓測試失去對外部契約的保真度，應回頭評估是否改用更真實的替身。

## Good Example

```md
選擇：
- 用 test DB 驗證 repository 行為
- 對第三方金流只 mock 真正的 HTTP client
- 對時間使用固定 clock fake
```

## Bad Example

```md
選擇：
- DB、repository、service、helper、DTO mapper 全部 mock
- 測試只剩「某某方法被呼叫過」
```
