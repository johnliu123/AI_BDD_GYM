# 反模式 — 先圖後碼

| 反模式 | 為何有害 | 應做 |
|---|---|---|
| 邊畫邊寫 | 使用者無法在低成本下改架構 | Phase 2 完成提案 → Phase 3 確認 |
| 整張 enterprise 圖 | 噪音大、難確認 | 只畫 in scope 類別 |
| 圖與程式漂移 | 後續維護失去單一真相 | 改碼前先修圖並再確認 |
| 無施工順序 | 循環依賴、大量 stub | Phase 4 先 THINK 依賴序 |
| 把核心邏輯塞進未命名 utils | 類別圖失效 | 責任須落在圖中類別 |

## 校準情境

**使用者：「做猜拳，直接写吧。」**  
仍須先 Phase 1–2 產出精簡類別圖並 Phase 3 確認；若使用者堅持跳過，說明風險並請其 **明確 waive** 確認閘，且回報時標註未走標準流程。

**使用者：「图 OK，但先改 GameEngine 多加一个方法。」**  
視為修訂：更新 Mermaid → 再次確認 → 再施工。
