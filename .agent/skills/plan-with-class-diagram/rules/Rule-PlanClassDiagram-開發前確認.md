# Rule 1 - 未取得同意前不得進入實作

- Level: `MUST`
- 在 Phase 3 收到使用者 **明確同意依目前類別圖施工** 之前，不得新增業務類別、不得重構目錄結構、不得大規模改介面。
- 允許在 Phase 1–2 的 **只讀** 盤點（讀檔、搜尋、理解慣例）。
- 使用者只說「再看看」或提出修圖，視為未同意，須修訂提案後再次確認。
- 使用者明確表示「先不要寫程式，只要圖」時，完成 Phase 2 後停止，不進 Phase 4。

## Good Example

- 這個例子是好的，因為先給圖並等待明確 OK。

````text
「以下是類別圖提案（Mermaid）。若同意我將依序實作 A → B → C；若要改請直接指出類別或關係。」
使用者：OK，照這張圖做 → 進入 Phase 4。
````

## Bad Example

- 這個例子是壞的，因為邊畫邊寫大量程式，使用者尚未確認。

````text
AI 產出草稿類別圖後，同則訊息已建立 5 個 .py 檔並改動 main。
````

# Rule 2 - 修訂優先於硬做

- Level: `MUST`
- 施工中若發現類別圖與需求或技術現實不符時，**停止擴大實作**，向使用者說明差異並更新類別圖；**重新確認後** 再繼續。
- 不得為了「已經寫一半」而悄悄偏離已確認的圖而不告知。

## Good Example

- 這個例子是好的，因為發現多一層 Repository 較合理，先修圖再寫。

````text
「實作 Service 時發現需抽 Repository；已更新 Mermaid 並標出新增類別，請確認後我再繼續。」
````

## Bad Example

- 這個例子是壞的，因為私下改架構且不更新圖。

````text
確認圖只有 Service，實作時加了 Repository 但未告知使用者。
````

# Rule 3 - 確認請求須具體可決策

- Level: `SHOULD`
- 請使用者確認時，須一併提供：Mermaid 圖、3–5 句設計摘要、主要假設、以及同意後的 **預計施工順序**（類別名列表即可）。
- 避免只丟圖不問「是否可以開始依圖開發」。

## Good Example

- 這個例子是好的，因為問題可回答是或否，且附順序。

````text
「是否同意依此類別圖開發？順序：Domain → GameEngine → CLI。」
````

## Bad Example

- 這個例子是壞的，因為沒有明確 gate。

````text
「這是類別圖。」（未問是否開始寫程式）
````
