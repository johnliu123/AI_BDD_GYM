# Rule 1 - 規格內容必須區分來源事實與未確認推論

- Level: `MUST`
- User Story、FR/NFR 與驗收情境只能表達使用者明確提供或經澄清確認的需求；推論不可寫成已確認事實。
- 對產出有影響但尚未確認的資訊，必須透過 `/clarify` 取得決策，或明確標記為假設／待確認事項；不得自行補入未被要求的行為。
- 不可自行新增來源未提供的效能門檻、比例、時限或承諾，並將其寫成已確認的成功標準。

## Good Example

- 這個例子是好的，因為來源沒有說明缺少拍攝日期時的行為，因此將其保留為待確認事項。

```md
假設／待確認：若照片沒有拍攝日期，應歸入哪個相簿尚未確認。
```

## Bad Example

- 這個例子是壞的，因為來源沒有指定缺少日期的處理方式，規格卻自行新增固定行為。

```md
- **FR-002**: 缺少拍攝日期的照片必須放入「日期未知」相簿。
```

# Rule 2 - 驗收情境與成功標準必須可驗證且有來源依據

- Level: `MUST`
- 每個 User Story 必須有多個可驗證的驗收情境；每個情境須說明前置條件、觸發行為及可觀察結果，並以 Given/When/Then 表達。
- NFR 必須描述可觀察或可驗證的品質結果；「直覺」、「快速」、「容易」等詞若沒有判準，必須標記為待確認，不可當作已完成的驗收條件。

## Good Example

- 這個例子是好的，因為 Given/When/Then 包含前置條件、觸發行為與可觀察結果。

```md
**驗收情境**：
1. **Given** 使用者位於主頁面，**When** 將照片拖放到同一相簿的新位置，**Then** 照片依新順序顯示。

**成功標準**：
- **SC-001**: 操作完成後，主頁面顯示的照片順序與已儲存順序一致。
```

## Bad Example

- 這個例子是壞的，因為缺少可觀察的預期結果，無法判定驗收是否通過。

```md
**驗收情境**：
1. **Given** 使用者在主頁面，**When** 使用者拖動照片，**Then** 操作成功。
```

# Rule 3 - 量測門檻必須有明確來源

- Level: `MUST`
- 成功標準中的比例、時間、數量或其他門檻，必須來自使用者明示或經澄清確認的內容。
- 沒有來源依據的門檻不可寫成已確認的成功標準；若確實需要該決策，透過 `/clarify` 確認，否則改寫為可觀察但不帶臆測數值的結果。

## Good Example

- 這個例子是好的，因為 3 秒門檻明確來自使用者確認的目標。

```md
來源已確認：使用者要求搜尋結果在 3 秒內顯示。
- **SC-001**: 95% 的搜尋結果在 3 秒內顯示。
```

## Bad Example

- 這個例子是壞的，因為來源未指定延遲上限，規格自行加入 1 秒門檻。

```md
- **SC-001**: 搜尋結果必須在 1 秒內顯示。
```
