# Rule 1 - 需求必須依適用的 User Story 範圍歸屬

- Level: `MUST`
- 只適用於一個 User Story 的 FR/NFR 必須列在該故事底下。
- 適用於兩個以上 User Story 的 FR/NFR 必須只在「全域需求」列一次，並標出所有適用故事；各故事以需求 ID 參照。
- 不適用於任何 User Story 的需求不可僅因難以分類就放入全域需求，應先澄清其產品目標或移至假設／待確認事項。

## Good Example

- 這個例子是好的，因為同一個跨故事需求只列一次，且兩個故事都有可追溯的參照。

```md
### User Story 1
全域需求參照：FR-003

### User Story 2
全域需求參照：FR-003

## 全域需求
- **FR-003**（適用於 User Story 1、2）: 操作完成後，照片順序必須保持一致。
```

## Bad Example

- 這個例子是壞的，因為同一個跨故事需求被重複定義在兩個故事下，形成多個正式版本。

```md
### User Story 1
- **FR-003**: 操作完成後，照片順序必須保持一致。

### User Story 2
- **FR-004**: 操作完成後，照片順序必須保持一致。
```

# Rule 2 - 每個需求 ID 必須唯一且穩定

- Level: `MUST`
- 每項正式 FR、NFR、**BR** 與 SC 必須有全文件唯一的 ID；User Story 對全域 FR/NFR 的參照沿用原 ID，不建立新 ID。
- 需求文字修訂時保留既有 ID；只有代表不同需求的新項目才配置新 ID。

## Good Example

- 這個例子是好的，因為正式需求只定義一次，故事參照沿用同一個 ID。

```md
### User Story 1
全域需求參照：NFR-002

## 全域需求
- **NFR-002**（適用於 User Story 1、2）: 頁面必須在 2 秒內呈現搜尋結果。
```

## Bad Example

- 這個例子是壞的，因為兩個不同需求共用同一個 ID，引用時無法判斷指向哪一項。

```md
- **FR-001**: 依拍攝日期建立相簿。
- **FR-001**: 允許拖放重新排列照片。
```

# Rule 3 - 全域需求參照必須與正式定義及適用故事一致

- Level: `MUST`
- 每個 User Story 的全域需求參照都必須對應到全域區正式定義的 FR/NFR。
- 全域需求標示的適用故事必須包含所有引用它的故事；無效或多餘參照視為追溯錯誤。

## Good Example

- 這個例子是好的，因為 User Story 1 的參照存在於全域定義中，且適用故事包含 User Story 1。

```md
### User Story 1
全域需求參照：FR-005

## 全域需求
- **FR-005**（適用於 User Story 1、2）: 相簿不得互相嵌套。
```

## Bad Example

- 這個例子是壞的，因為 User Story 1 引用 FR-005，但全域需求未列出該 ID。

```md
### User Story 1
全域需求參照：FR-005

## 全域需求
- **FR-006**（適用於 User Story 2）: 相簿不得互相嵌套。
```
