# Rule 1 - 整體驗收 Feature 必須直接放在 acceptance 目錄

- Level: `MUST`
- 每個 spec package 的總驗收 Gherkin 必須輸出為一份 `.feature`，直接放在 `specs/<feature>/features/acceptance/`。
- 不得依前端、後端或模組切分成多份 Feature；此階段也不得建立 `dsl.md`。

## Good Example

- Feature 直接位於 acceptance 目錄，描述跨完整系統流程的驗收。

```text
specs/001-checkout/features/acceptance/顧客完成下單.feature
```

## Bad Example

- Feature 被放進前端子目錄，違反單一總驗收產物的落點要求。

```text
specs/001-checkout/features/frontend/結帳頁.feature
```

# Rule 2 - Example 必須呈現少量完整的使用者旅程

- Level: `MUST`
- 每個 Example 必須描述可從起始業務情境走到可觀察驗收結果的完整 Journey，而非單一畫面或孤立 API 行為。
- 新增 Example 必須對應不同的核心旅程、會改變驗收結果的業務規則變體，或重要失敗／恢復分支；只有輸入資料不同、流程與預期結果相同的情境不得另開 Example。
- Given / When / Then 使用 PM 可理解的業務語言，Then 應呈現顧客、訂單或商業規則可觀察到的結果。
- 每個 Example 的最後一行 MUST 為 `# 驗收結果：<一句話摘要>`，讓讀者不必重讀整段 Then 即可掌握本案例驗了什麼。

## Good Example

- 顧客從挑選商品開始，經過套用優惠與付款，最後驗證訂單金額及結果。

```gherkin
Example: 顧客套用符合資格的優惠後完成付款
  Given 顧客選購了符合活動條件的商品
  When 顧客套用優惠並完成付款
  Then 顧客取得金額正確的已付款訂單
  # 驗收結果：優惠生效 + 付款成功 + 訂單金額正確
```

## Bad Example

- 案例只檢查單一步驟，無法示範 PM 要驗收的完整系統流程。

```gherkin
Example: 優惠碼顯示成功
  Given 顧客位於結帳畫面
  When 顧客輸入優惠碼
  Then 畫面顯示成功
```

# Rule 3 - 待澄清問題必須使用指定標籤且數量介於一至十個（例外零）

- Level: `MUST`
- 尚未確認且會影響需求解讀或驗收結果的問題，必須使用 Gherkin 註解格式 `# [need clarification] <問題>`。
- 每次產出的 Feature **MUST 包含 1 至 10 個**待澄清標籤，當 spec 或本輪 Journey 仍存在符合下方品質判準、且尚未由 spec 明確回答的缺口時。
- 只有滿足以下**至少一個**條件的問題才值得標記：
  - a) 答案會改變至少一個驗收結果的預期（Given / When / Then）
  - b) 答案會新增或移除一個完整的 Rule 或 Example
  - c) spec 中存在相互矛盾的陳述
- **例外**：若 spec 已足夠明確且**無**符合 a/b/c 的問題，可以 **0 個**標籤產出，但 MUST 在交付摘要中說明「本輪無需澄清」的判斷依據（並說明已檢查 spec 假設、Then 一致性、Rule 可推導性）。
- 不得把已由 spec 明確回答的事項重複標記；**不得為湊數捏造低價值問題**；不得在仍有符合 a/b/c 的缺口時刻意少標或不標。

## Good Example

- 在實際規則附近提出三個由驗收決策引出的問題。

```gherkin
  # [need clarification] 優惠門檻以商品折扣前或折扣後的金額計算？
  And 顧客符合優惠門檻
  # [need clarification] 付款失敗時，優惠資格是否保留供顧客重試？
  When 顧客完成付款
  # [need clarification] 訂單成立後是否仍可取消並取回已折抵點數？
  Then 顧客取得已付款訂單
```

## Bad Example

- spec 仍有會改變 Then 的未決政策，卻完全不標記（應至少 1 個符合品質判準的標籤）；或以無驗收影響的問題湊數。

```gherkin
  # spec 未說明付款失敗後優惠是否保留，但本 Example 未標記任何待澄清
  Then 顧客可以沿用原購物車再次付款
```

```gherkin
  # [need clarification] 顧客是否喜歡這個畫面顏色？
  Then 顧客取得已付款訂單
```

# Rule 4 - 澄清標籤必須緊鄰受影響的業務規則或驗收步驟

- Level: `MUST`
- 標籤必須放在其所詢問的 Given、When、Then 或相關業務規則旁，使讀者能辨識答案會改變哪個驗收條件。
- 澄清內容必須詢問業務政策、流程選擇或可觀察結果；不得把技術實作選擇偽裝成 PM 的需求問題。

## Good Example

- 問題緊鄰受付款失敗影響的資源狀態驗收。

```gherkin
  # [need clarification] 付款遭拒後，購物車與優惠資格是否都應保留？
  Then 顧客可以沿用原購物車再次付款
```

## Bad Example

- 問題集中在不相干的檔尾備註，無法指出它影響哪一個驗收步驟。

```gherkin
  Then 顧客可以沿用原購物車再次付款

  # [need clarification] 這個流程應使用哪種資料庫索引？
```

# Rule 5 - Feature 完成後依標籤狀態決定是否 Clarify

- Level: `MUST`
- 完成 Feature 與 `情境地圖.md` 後：若仍有 1 個以上待澄清標籤，MUST 立即委派 `/clarify`，不得先進入技術研究或其他下游流程。
- 若待澄清標籤為 0 個且符合 `/clarify` 豁免判準，可跳過 `/clarify` 並在交付摘要列出依據。
- 依使用者旅程順序與決策影響排序提問；每輪 1 至 3 題、單一 clarify session 最多 5 題。超過 5 個標籤時，完成目前 session 後再以新 session 繼續。
- 使用者回答後，將決策回填 Feature 並移除已解決標籤；使用者明確保留待決的事項不得自行推定答案。

## Good Example

- 先產出旅程與問題，再立即逐批詢問並將回答反映回同一份 Feature。

```text
產出 Feature 與 6 個標籤 → /clarify 依序澄清 → 回填答案 → 新 session 澄清剩餘問題
```

## Bad Example

- 標籤尚未交由使用者決策，就先開始技術研究或自行將假設寫成已確認規則。

```text
產出 Feature 與 6 個標籤 → 自行選定規則 → /technical-research
```

# Rule 6 - 此階段不得定義 DSL 或前後端實作語意

- Level: `MUST`
- Feature 只定義跨系統的總驗收條件，不得出現 endpoint、HTTP、selector、資料庫 schema、step definition 或測試框架操作。
- 本階段不得產生 `dsl.md`；各 Gherkin 句子的測試語意留待後續系統分析後處理。

## Good Example

- Gherkin 描述使用者能觀察到的業務結果。

```gherkin
Then 顧客取得包含正確折扣與應付金額的已付款訂單
```

## Bad Example

- Gherkin 暴露 HTTP 與資料存取實作，超出總驗收需求。

```gherkin
Then API 回傳 HTTP 201 並在 orders 資料表新增一筆紀錄
```

# Rule 7 - Background 只能抽出所有旅程共用且具有驗收語意的步驟

- Level: `MUST`
- Journey 型 Feature 預設不使用 `Background`；不得只因多個 Example 重複相同前置資料或設定，就把它們抽出。
- 只有當步驟本身表達所有 Example 共用的業務前提或驗收語意，且抽出後仍能清楚理解每個 Journey 時，才可使用 `Background`。
- 顧客登入狀態、帳戶數值、商品資料、折扣門檻、運費或規則設定表等測試資料與設定，應留在各自 Example，讓每段 Journey 可獨立閱讀及 DEMO。

## Good Example

- 所有旅程都以會員資格作為共同業務前提；抽出後仍清楚表達本 Feature 驗收的是會員專屬旅程。

```gherkin
Feature: 會員使用會員專屬服務

  Background:
    Given 顧客具有有效會員資格

  Rule: 有效會員可使用會員專屬服務
```

## Bad Example

- Background 只收納登入與測試設定資料，讓每個完整 Journey 的必要條件藏在共用區。

```gherkin
Feature: 顧客完成下單

  Background:
    Given 顧客「林小姐」已登入，且有 500 點
    And 結帳折扣門檻為 2000 元，運費為 100 元

  Example: 顧客使用折扣碼下單
```

# Rule 8 - 必須產出情境地圖摘要

- Level: `MUST`
- Phase 2 完成後，MUST 在 `features/acceptance/` 同目錄產出 `情境地圖.md`，依 `templates/情境地圖.template.md` 以樹狀／清單呈現核心旅程、關鍵變體、邊界與待澄清狀態。
- 情境地圖是 PM 快速 Review 的入口，不取代 `.feature` 的驗收權威。
