# Rule 1 - 根因必須由重現情境中的首個分歧及證據支持

- Level: `MUST`
- 優化既有 Skill 時，診斷必須以使用者提供的失敗情境為起點，說明該情境的預期結果與實際結果。
- 必須重走受影響的 SOP，檢查相關上游／下游 Skill 及該流程實際載入的模組，定位預期與實際結果首次分歧的步驟或資源。
- 根因必須連結到可觀察證據及造成的落差；若證據不足以區分多個可能原因，必須繼續調查或向使用者說明不確定性，不可將猜測當作已確認根因。

## Good Example

- 這個例子是好的，因為它重現了具體輸入，指出第一個分歧發生在模板載入步驟，並以實際 SOP 路徑支持根因。

````text
預期：產出包含標題、風險與驗收條件的變更提案。
實際：只產出標題與摘要。
重現：依目標 Skill 的 SOP 提供同一段使用者需求，逐步執行至提案輸出。
首個分歧：SOP 要求載入的模板只有標題與摘要欄位。
證據：templates/change-proposal.md 缺少風險與驗收條件欄位。
根因：輸出缺漏源自模板結構不足，不是執行模型忽略了已有欄位。
````

## Bad Example

- 這個例子是壞的，因為它只根據結果推測模型不遵循指示，未重現流程或檢查被載入的資源。

````text
實際結果少了風險欄位，所以應該在 SKILL.md 加一句「不要漏掉風險」。
````

# Rule 2 - 根因與修改範圍必須先經使用者確認

- Level: `MUST`
- 實作前必須向使用者說明預期結果、實際落差、首個分歧、根因及受影響範圍，並取得使用者對診斷的確認。
- 使用者不同意診斷時，必須依回饋補充或修正調查，再次確認；確認前不可提出編排方案、呼叫 form／derive Skill 修改資源，或直接編輯目標檔案。

## Good Example

- 這個例子是好的，因為它提出可驗證的根因和明確範圍，並在使用者確認前停留於診斷階段。

````text
診斷：templates/change-proposal.md 缺少風險與驗收條件欄位，導致重現情境中兩項輸出缺漏。
範圍：只涉及該模板及目標 SOP 載入此模板的步驟。
請確認這是否符合你觀察到的問題；確認前我不會提出或執行修改方案。
````

## Bad Example

- 這個例子是壞的，因為未取得根因與範圍確認就立即修改檔案。

````text
我推測模板太短，先把模板和 SOP 一起重寫，再請使用者看看是否修好。
````
