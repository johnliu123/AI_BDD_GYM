# Rule 1 - 新建或優化時必須先有可執行的 SOP 基礎

- Level: `MUST`
- 新建 Skill 時，必須先形成最小可執行的 SOP，才逐步判斷是否需要額外模組。
- 優化既有 Skill 時，必須以確認的根因為依據，指出受影響的 SOP step；未受影響且仍有效的流程不得為了重寫而重寫。
- SOP step 必須描述操作者要完成的動作與預期產出；細部判準、固定輸出格式和確定性自動化分別由 Rule、Template、Script 承載。

## Good Example

- 這個例子是好的，因為先定義由誰執行、讀取什麼、產出什麼，再從具體 step 評估資源需求。

````md
1. READ 讀取變更需求與受影響檔案。
2. THINK 判斷影響範圍並整理風險。
3. WRITE 產出包含影響範圍、風險與驗收條件的變更提案。
````

## Bad Example

- 這個例子是壞的，因為還沒有可執行流程，就先加入孤立的模板和腳本，無法說明它們支援哪個 step。

````text
新增 templates/proposal.md 和 scripts/build_proposal.py，但 SOP 沒有任何步驟讀取或執行它們。
````

# Rule 2 - Deriver 必須依 step 的實際需求選用，不為模組化而模組化

- Level: `MUST`
- 需要明確判定標準、合格條件或容易反覆出錯的要求時，才評估 `/skill-derive-rule`。
- 產出有穩定結構且部分內容需替換時，才評估 `/skill-derive-template`。
- 工作可由明確輸入和確定性程序自動完成時，才評估 `/skill-derive-script`；語意判斷、權衡及使用者決策必須留在人工作業流程。
- 每個 step 可同時採用多個模組，但每一個都必須對應獨立且明確的需求；沒有足夠收益時保留在 SOP，不新增模組。

## Good Example

- 這個例子是好的，因為它分別指出格式、可確定性計算與 AI 判斷的責任，並只為前兩者配置適合的模組。

````text
指定 step：將測試結果整理成報告並判斷是否符合需求。
Rule：報告必須包含通過數、失敗數與失敗案例。
Template：報告有固定章節，資料值每次不同。
Script：讀取測試 JSON 並計算通過數、失敗數及列出失敗案例。
保留 AI：依需求判斷失敗是否可接受並決定是否修正。
````

## Bad Example

- 這個例子是壞的，因為它為每個 step 強制建立三種模組，且將需要判斷需求的工作交給腳本。

````text
所有 step 都新增 RuleFile、Template 和 Python script；腳本自行判斷測試失敗是否符合產品需求。
````

# Rule 3 - 實作前必須核准包含變更取捨的編排方案

- Level: `MUST`
- 方案必須列出候選 SOP 的 step、各模組採用或不採用的理由、預計新增／修改／移除的檔案、根因對應方式及驗收情境。
- 新建 Skill 與優化既有 Skill 都必須在寫入或委派修改檔案前取得使用者對方案的明確同意；使用者尚未同意或要求調整時，只能修訂方案，不能開始實作。
- 優化既有 Skill 時，方案可以提出刪除或取代無效架構的根本改動，不得只因偏好小 diff 而保留已確認的根因；實作範圍仍須符合已確認問題及核准方案。

## Good Example

- 這個例子是好的，因為它明列根因、取捨、檔案變更與驗收方法，並先等待使用者核准。

````text
根因：現有摘要腳本把需要 AI 判斷的欄位硬編碼，無法處理不同需求。
方案：移除該判斷邏輯，保留腳本的確定性統計；新增報告模板；修改 SOP，將結果解讀留給 AI。
檔案：修改 scripts/summarize.py、templates/report.md 與 SOP；刪除已失效的規則引用。
驗收：重跑原失敗輸入，確認統計正確且 AI 仍依需求解讀結果。
請確認方案；核准後才開始修改。
````

## Bad Example

- 這個例子是壞的，因為直接以「先試試看」為由改檔，使用者無法在實作前審核影響和取捨。

````text
我先小改 SOP、加一條規則和一個腳本，之後再看結果要不要保留。
````

# Rule 4 - 每個資源變更必須有單一明確的編輯責任

- Level: `SHOULD`
- `/skill-form-sop` 負責建立基礎 SOP 或修改不屬於特定模組接回的流程；每個 `/skill-derive-*` 負責其指定模組需求、委派配對 `/skill-form-*`，並依其流程把模組接回指定 step。
- 編排時應明確指定每個檔案由哪個流程負責修改，避免同一段 SOP 接回工作重複委派或互相覆寫。
- 若所選 derive skill 的既有流程包含 SOP 編輯，應讓該流程負責對應模組的接回；只有其責任範圍以外的基礎 SOP 或流程變更才另交 `/skill-form-sop`。

## Good Example

- 這個例子是好的，因為基礎 SOP 與模板接回由不同責任者依序處理，各自只編輯負責範圍。

````text
1. 由 /skill-form-sop 建立基礎 SOP。
2. 由 /skill-derive-template 推導模板需求、委派 /skill-form-template 建立模板，並接回模板路徑。
3. 由 skill-engineering 驗收 SOP 與模板引用，不再次委派其他 Skill 重寫相同接回步驟。
````

## Bad Example

- 這個例子是壞的，因為 form-sop 與 derive-template 同時被要求改寫同一段模板載入步驟，責任重疊且可能互相覆寫。

````text
同時委派 /skill-form-sop 和 /skill-derive-template 插入同一份模板的 READ step。
````

# Rule 5 - 驗收必須覆蓋資源連結、任務情境與根因修復

- Level: `MUST`
- 實作後必須讀取目標 `SKILL.md` 與本次新增或修改的資源，確認每個檔案路徑有效、引用位於實際使用該資源的 step，且載入條件符合任務情境。
- 必須執行各資源可用的結構驗證；有腳本時，以安全且具代表性的輸入檢查輸入、輸出和錯誤處理。
- 優化既有 Skill 時，必須重跑已確認的失敗情境；建立新 Skill 時，必須走查代表性使用情境。未達預期時修正受影響部分並重跑驗證，不得只以檔案存在或格式通過宣告完成。

## Good Example

- 這個例子是好的，因為它驗證了引用、執行結果和原失敗情境，而不是只檢查新檔是否存在。

````text
- SOP 的 READ 路徑均存在，且只在需要產出報告時載入。
- RuleFile validator 通過。
- 以原本的測試資料重走 SOP，確認報告欄位完整且統計值正確。
- 失敗情境通過後才回報完成。
````

## Bad Example

- 這個例子是壞的，因為只建立了資源檔，沒有確認 SOP 引用或重跑問題情境。

````text
確認 templates/report.md 已建立，就回報優化完成。
````
