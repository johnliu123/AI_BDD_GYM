# SOP

## Phase 1 -- 界定工程模式與範圍

1. THINK 判斷本次任務是建立新 Skill，或優化既有 Skill，並確認目標 Skill、使用情境及使用者要求的結果。
2. READ 建立新 Skill 時，讀取使用者需求與相關範例；優化既有 Skill 時，讀取目標 `SKILL.md`、使用者提供的問題情境，以及受影響步驟直接引用的資源，僅沿相關引用繼續追查。

## Phase 2 -- 診斷並確認既有問題（僅優化模式）

1. READ 只有在優化既有 Skill 時，才讀取 `rules/Skill-Engineering-根因診斷與確認.md`，依其要求分析問題與確認根因。
2. THINK 僅在優化模式下，依使用者提供的對話、輸入及失敗結果重走受影響的 Skill 流程；追查相關上下游 Skill 與被載入的模組，找出預期與實際結果首次分歧的位置及根因證據。
3. WRITE 僅在優化模式下，向使用者說明預期結果、實際結果、流程中的分歧位置、根因及受影響範圍，並請使用者確認問題診斷。
4. THINK 若使用者不同意根因或範圍，依回饋補充調查並重新確認；根因與範圍獲確認前，不提出模組編排方案、不修改任何檔案。

## Phase 3 -- 建立 SOP 基礎並提出編排方案

1. READ 讀取 `rules/Skill-Engineering-模組編排與變更治理.md`，依其判準安排 SOP、模組選擇、變更提案及驗收。
2. THINK 依 `/skill-form-sop` 的方法整理最小可執行的候選 SOP；建立模式整理新流程，優化模式只規劃根因所需的 SOP 變更並保留未受影響部分，此步不修改檔案。
3. READ 建立模式讀取相關範例與上下文；優化模式讀取現有 SOP 及相關模組，逐步檢視輸入、動作、預期產出和目前的模組引用。
4. THINK 逐步判斷候選 SOP 中是否需要 `/skill-derive-rule`、`/skill-derive-template` 或 `/skill-derive-script`；沒有明確的品質、格式或自動化收益時，保留在 SOP，不新增模組。
5. WRITE 向使用者提出完整編排方案，列出候選 SOP、每個 step 採用或不採用的模組及理由、預計新增／修改／移除的檔案、根因對應方式與驗收方法；請使用者確認方案後再寫入或委派修改任何檔案。

## Phase 4 -- 依核准方案實作並驗收

1. THINK 若使用者未確認方案，依回饋修訂方案並再次確認，不開始實作。
2. DELEGATE 依核准方案委派 `/skill-form-sop` 建立新 Skill 的 SOP 或修改既有 SOP；重新讀取實際 SOP，若變更超出核准方案，先停下並請使用者確認調整方案。
3. DELEGATE 依核准的 step 與模組清單，逐項委派對應的 `skill-derive-*`；由各 derive skill 使用其配對的 `skill-form-*` 建立或修改資源並接回 SOP，不重複委派其他 Skill 修改相同內容。
4. WRITE 依核准的根因修正目標範圍內失效、冗餘或不適用的流程與模組；不為保留舊架構而只加表層補丁，亦不改動與目標無關的內容。
5. READ 重新讀取目標 Skill 與本次變更的全部模組，確認路徑、載入時機、執行契約及 SOP 互相一致，並執行相關結構或腳本驗證。
6. THINK 優化既有 Skill 時，以原問題情境重走流程，確認根因已消除且未引入回歸；建立新 Skill 時，以代表性任務走查觸發條件、SOP 與模組交接。發現問題時修正並重跑受影響的驗證。
7. WRITE 向使用者回報根因與方案的確認結果、實際變更、驗證結果及尚未解決的限制。
