# 功能規格：點餐系統第三迭代－訂單建立與查詢

**功能分支**：`003-order-creation-inquiry`

**建立日期**：2026-10-13

**狀態**：草稿

**輸入**：使用者描述：「請設計並開發一套完整的點餐系統，提供顧客瀏覽餐點、查看價格、選擇餐點規格與數量、加入購物車、確認訂單及查詢訂單狀態等功能，並提供店家管理介面，讓管理人員可以維護餐點分類、餐點資訊、價格、供應狀態及訂單資料。系統需具備訂單金額計算、訂單狀態管理、付款狀態管理及訂單紀錄查詢等功能，並確保資料正確性、避免重複送單、驗證餐點供應狀態及防止前端竄改訂單金額。此需求分成 6 次迭代開發；請先開發 03 項目。03：訂單建立與查詢，產生訂單編號、保存訂單明細、查詢訂單狀態。」

## 商業規則 *(必要)*

- **BR-001**: 訂單金額須於建立當下由伺服器依目前餐點價格、所選規格加價與數量計算，並將單價與項目／訂單金額以快照寫入訂單明細；建立後查詢與呈現須以該快照為準，不得採信顧客端提交的金額，也不得在查詢時以最新菜單價格覆寫已成立訂單金額。（對應需求：**FR-003**、**FR-011**）
- **BR-002**: 建立訂單前須再次驗證購物車內每一項餐點與所選規格均為供應中；只要存在不可用項目，整筆訂單不得成立。（對應需求：**FR-004**、**FR-005**）
- **BR-003**: 每筆成功建立的訂單須具備全系統唯一且可供顧客引用的訂單編號；同一有效訪客工作階段內，以相同冪等鍵重送建立請求不得產生第二筆訂單。（對應需求：**FR-002**、**FR-007**）

## 使用者情境與測試 *(必要)*

### 使用者故事 1 - 從購物車確認並建立訂單 (優先順序：P1)

身為持有有效訪客工作階段的顧客，我想依目前購物車內容送出訂單並取得訂單編號，以便完成點餐並保留訂單紀錄。

**為何這個優先順序**：訂單建立是將購物車轉為正式交易紀錄的核心步驟；沒有持久化訂單，後續查詢與店家流程無法銜接。

**獨立測試**：準備含多項可用餐點的購物車，以有效訪客工作階段送出建立訂單；確認回應含唯一訂單編號、與購物車一致的明細及伺服器計算的快照金額。再測空車、含不可用項目、重複冪等鍵、以及夾帶竄改總額的請求。

**驗收情境**：

1. **Given** 訪客持有有效工作階段，且該工作階段購物車有多項可用餐點，**When** 訪客送出建立訂單請求，**Then** 系統產生唯一訂單編號、保存訂單標頭與各項明細（含餐點名稱、所選規格、數量及建立當下的單價與項目金額快照），並回傳訂單初始狀態為「已建立」及訂單總金額。
2. **Given** 訪客購物車中至少有一項不可用餐點，**When** 訪客嘗試建立訂單，**Then** 系統拒絕建立，不產生訂單編號，且購物車內容維持不變。
3. **Given** 訪客購物車沒有任何可用項目（空車或僅含不可用項目），**When** 訪客嘗試建立訂單，**Then** 系統拒絕建立，且不寫入訂單資料。
4. **Given** 訪客已成功建立一筆訂單，且建立請求含有伺服器先前接受過的冪等鍵，**When** 訪客以相同冪等鍵再次送出建立訂單，**Then** 系統回傳同一筆訂單的結果，不得新增第二筆訂單。
5. **Given** 建立訂單請求的 body 含有顧客自行填寫的訂單總金額或項目金額，**When** 系統建立訂單，**Then** 持久化與回應的金額僅依伺服器計算的快照，與顧客端欄位無關。
6. **Given** 訪客已成功建立訂單，**When** 建立流程完成，**Then** 該工作階段購物車中已納入訂單的項目被清空，顧客看到空購物車。

**功能需求（FR）**：

- **FR-001**: 系統必須允許持有有效訪客工作階段的顧客，依該工作階段購物車內容送出建立訂單請求。
- **FR-002**: 系統必須在訂單成功建立時產生全系統唯一、可供顧客引用的訂單編號。
- **FR-003**: 系統必須持久化訂單標頭（含訂單編號、建立時間、初始訂單狀態、訂單總金額快照）及訂單明細（餐點識別、顯示名稱、所選規格摘要、數量、建立當下單價與項目金額快照）。
- **FR-004**: 系統必須在建立訂單前再次驗證購物車每一項的餐點供應狀態與所選規格有效狀態；任一項不可用時整筆拒絕。
- **FR-005**: 系統必須在購物車沒有任何可用項目時拒絕建立訂單。
- **FR-006**: 系統必須在訂單成功建立後清空該訪客工作階段的購物車。
- **FR-007**: 系統必須支援建立訂單請求的冪等鍵；相同有效訪客工作階段與相同冪等鍵的重送不得建立多筆訂單，須回傳原訂單結果。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-011

### 使用者故事 2 - 查詢訂單狀態與明細 (優先順序：P1)

身為曾於同一瀏覽器工作階段建立訂單的顧客，我想以訂單編號查詢該筆訂單的狀態與明細，以便確認訂單內容與目前狀態。

**為何這個優先順序**：查詢是第三迭代明確交付項目；顧客在建立訂單後需能自行核對紀錄，無須等待店家介面（屬後續迭代）。

**獨立測試**：建立訂單後，以同一訪客工作階段查詢該訂單編號，確認狀態、明細與快照金額一致；以不同工作階段或不存在編號查詢，確認拒絕或查無。

**驗收情境**：

1. **Given** 訪客持有有效工作階段，且該工作階段曾成功建立一筆訂單，**When** 訪客以該訂單編號查詢訂單，**Then** 系統回傳該訂單的訂單狀態、訂單編號、建立時間、明細及持久化的快照金額。
2. **Given** 訂單建立後菜單價格或規格加價已變更，**When** 訪客查詢該訂單，**Then** 回傳的單價、項目金額與訂單總金額仍為建立當下快照，不因最新菜單價格而改變。
3. **Given** 另一個具有不同伺服器簽發工作階段的瀏覽器，**When** 該瀏覽器以第一個工作階段所建立訂單的編號查詢，**Then** 系統不得揭露該訂單內容（回傳查無或等同拒絕存取）。
4. **Given** 訪客持有有效工作階段，**When** 訪客以不存在或不屬於該工作階段的訂單編號查詢，**Then** 系統回傳查無或等同拒絕，且不洩漏其他訂單是否存在。

**功能需求（FR）**：

- **FR-008**: 系統必須允許持有有效訪客工作階段的顧客，以訂單編號查詢由同一工作階段建立的訂單。
- **FR-009**: 系統必須在查詢成功時回傳訂單狀態、訂單編號、建立時間、訂單明細及持久化的快照金額。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-011

### 邊界情況

- 建立訂單與查詢訂單皆須綁定伺服器驗證的訪客工作階段；不得接受客戶端自報的工作階段識別或登入帳號作為訂單歸屬或查詢授權依據。
- 購物車僅含不可用項目時視同無可用項目，不得建立訂單。
- 建立訂單時若餐點在購物車檢視時可用、送出瞬間變為不可用，伺服器以建立當下驗證結果為準並拒絕整筆訂單。
- 冪等鍵缺漏時，每次有效建立請求仍須獨立處理；有冪等鍵時才套用 BR-003 的重送語意。
- 伺服器對 `(guest_session_id, Idempotency-Key)` 的冪等結果預設保留 **24 小時**（與第二迭代訪客 session **idle 24 小時**對齊）；`expires_at` 過期後相同 key 視為新請求。部署可透過環境設定覆寫 TTL，但不得短於單次合理重試窗口到零。
- 建立訂單若回 **4xx**（驗證／業務拒絕）或 **5xx**（伺服器／交易失敗）且**未**成功持久化訂單，不得寫入冪等成功紀錄；客戶端可修正 cart 後重試。僅 **201** 新建立或 **200** 冪等命中時，才持久化／回傳已成立訂單結果。
- 本迭代訂單狀態僅包含顧客建立當下的初始狀態「已建立」；店家接單、出餐或完成等狀態轉換不在本迭代範圍。
- 訂單總金額為各明細快照項目金額之和，不包含未在需求中指定的稅金、運費、折扣、服務費或付款手續費。

## 全域需求 *(僅於存在跨多個 User Story 的需求時納入)*

### 功能需求（FR）

- **FR-010**（適用於使用者故事 1、2）: 訂單建立與查詢必須綁定伺服器簽發並透過 HttpOnly cookie 傳遞的有效訪客工作階段；訂單僅能由建立該訂單的同一工作階段查詢，不同工作階段互相隔離。本功能不提供登入帳號綁定、跨裝置同步或以訂單編號單獨向任意訪客公開查詢。
- **FR-011**（適用於使用者故事 1、2）: 訂單相關金額須由伺服器在建立時計算並以快照持久化；顧客端提交的訂單總金額、項目金額或單價不得作為寫入或查詢回應的計價依據。

### 主要實體 *(若功能涉及資料則納入)*

- **訪客工作階段**：與第二迭代相同，由伺服器簽發的匿名工作階段識別；作為購物車與訂單歸屬及查詢授權依據。
- **訂單**：顧客一次成功送單的紀錄；含唯一訂單編號、初始訂單狀態、建立時間、訂單總金額快照及與建立工作階段的關聯。
- **訂單明細**：訂單中的餐點列；含餐點與規格識別、顯示用名稱、數量，以及建立當下的單價與項目金額快照。
- **冪等鍵**：顧客端在建立訂單請求中提供的去重識別；與訪客工作階段配對後用於避免重複送單。

## 成功標準 *(必要)*

### 可衡量成果

- **SC-001**: 從僅含可用項目的購物車成功建立訂單後，回傳的訂單編號唯一，且明細的餐點、規格、數量與購物車一致。
- **SC-002**: 訂單總金額與各明細項目金額等於建立當下依伺服器目前餐點價格、規格加價與數量計算的快照結果；與顧客端提交的金額欄位無關。
- **SC-003**: 含不可用項目、空車或僅不可用項目的購物車無法建立訂單，且未寫入訂單資料。
- **SC-004**: 相同工作階段與相同冪等鍵重送建立請求時，系統僅存在一筆對應訂單，重送回應與首次成功結果一致。
- **SC-005**: 同一工作階段可以訂單編號查詢到剛建立的訂單狀態與快照明細；不同工作階段無法查詢到該訂單內容。
- **SC-006**: 訂單成功建立後，該工作階段購物車為空；再次建立訂單須先重新加入餐點。

## 假設

- 第一、二迭代已提供訪客工作階段、購物車、餐點供應狀態、規格選擇及伺服器權威購物車計價；本迭代在此基礎上擴充訂單持久化與查詢。
- 本迭代不提供登入、註冊或帳號管理；訂單僅能由建立訂單的同一瀏覽器工作階段查詢，不支援跨裝置僅憑訂單編號查詢。
- 訂單建立成功後的初始訂單狀態固定為「已建立」；店家接單、製餐、完成及相關狀態更新屬第四迭代，本迭代不實作狀態轉換 API 或店家介面。
- 付款、付款狀態變更、訂單取消及退款屬第五迭代；本迭代不建立付款流程，也不持久化付款狀態欄位，除非後續分析為第四迭代預留欄位（預留本身不構成本迭代驗收）。
- 冪等鍵由顧客端在 `POST` 建立訂單請求以 **`Idempotency-Key` header** 提供（1–128 字元）；缺漏時每次有效請求獨立建單。
- 訂單編號格式為 **`ORD-` + UTC `YYYYMMDD` + `-` + 8 位大寫十六進位**，須全系統唯一且可供顧客引用（詳見 API 契約與 `plan.md` 設計決策·訂單編號）。
- 訂單明細的顯示名稱與規格摘要由伺服器在建立時自菜單資料擷取並快照，避免日後菜單更名導致歷史訂單無法辨識。

## 澄清紀錄

### Session 2026-10-13（clarify-over-specs · F1/F2）

- Q12: 冪等鍵結果保留多久？ → A: **預設 24 小時**，與第二迭代訪客 session idle（Q10）對齊；以 `order_idempotency_keys.expires_at` 強制；環境變數（如 `IDEMPOTENCY_TTL_MS`）可覆寫。
- Q13: 建立訂單回 5xx 或 4xx 時是否寫入冪等紀錄？ → A: **不寫入**（未成功建單）；僅 201 新單或 200 冪等命中時才有持久化冪等映射；5xx 允許客戶端重試同一 key。
- Q14: 訂單編號格式是否定案？ → A: **`ORD-YYYYMMDD-XXXXXXXX`（8 hex）**；與 research 及 `contracts/http-api.yaml` path pattern 一致。
