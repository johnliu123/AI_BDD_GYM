# 功能規格：點餐系統第六迭代－進階功能與系統驗證

**功能分支**：`006-advanced-features-system-verification`

**建立日期**：2026-10-14

**狀態**：草稿

**輸入**：使用者描述：「請設計並開發一套完整的點餐系統，提供顧客瀏覽餐點、查看價格、選擇餐點規格與數量、加入購物車、確認訂單及查詢訂單狀態等功能，並提供店家管理介面，讓管理人員可以維護餐點分類、餐點資訊、價格、供應狀態及訂單資料。系統需具備訂單金額計算、訂單狀態管理、付款狀態管理及訂單紀錄查詢等功能，並確保資料正確性、避免重複送單、驗證餐點供應狀態及防止前端竄改訂單金額。此需求分成 6 次迭代開發；請先開發 06 項目。06：進階功能與系統驗證，新增餐點售完管理、權限控管（RBAC）、例外處理以及整合測試。」

## 商業規則 *(必要)*

- **BR-001**: 餐點與規格的「供應中／停止供應」以持久化 `is_active` 為唯一權威；顧客端顯示、加入購物車、建單與金額計算須以伺服器讀取的最新狀態為準，不得採信客戶端自報的供應旗標。（對應需求：**FR-011**、**FR-013**）
- **BR-002**: 已成立訂單之明細與 `total_amount` 快照不受後續菜單價格或供應狀態變更影響；第六迭代對訂單的驗證僅限「建立當下」與查詢呈現，不得回寫歷史訂單金額。（對應需求：**FR-012**、第三迭代 **BR-001**）
- **BR-003**: 店家寫入菜單資料與操作訂單出餐／付款檢視為不同權限能力；持有僅訂單權限的憑證不得變更分類、餐點、價格或供應狀態，持有僅菜單權限的憑證不得接單或推進出餐狀態。（對應需求：**FR-010**、**FR-014**）
- **BR-004**: 對外 API 錯誤回應須使用穩定 `error.code` 與可顯示之中文 `message`；不得因未處理例外而回傳堆疊、原始 SQL 或內部路徑。（對應需求：**NFR-010**）

## 使用者情境與測試 *(必要)*

### 使用者故事 1 - 店家維護餐點分類與餐點資料 (優先順序：P1)

身為具菜單管理權限的店家管理人員，我想維護餐點分類、餐點名稱、圖片、價格及所屬分類，以便菜單內容與定價能隨營運更新並正確呈現給顧客。

**為何這個優先順序**：整體產品願景與 roadmap **06** 前的迭代刻意將「維護餐點分類、餐點資訊、價格」留待本迭代；沒有持久化寫入能力，售完管理與端到端驗證無法完整閉環。

**獨立測試**：以具 `menu` 或 `admin` 角色之店家憑證建立／更新分類與餐點；顧客端 `GET /menu-items` 反映變更；以僅 `orders` 角色憑證嘗試相同寫入均被拒絕。

**驗收情境**：

1. **Given** 管理人員持有有效且具 **menu** 或 **admin** 能力之店家憑證，**When** 建立新分類並新增一筆含名稱、價格、分類與可選圖片 URL 的餐點，**Then** 持久化成功且顧客菜單 API 可讀到新餐點與正確欄位。
2. **Given** 系統已有餐點，**When** 管理人員更新該餐點名稱、價格或分類，**Then** 持久化更新成功；顧客重新載入菜單時看到新值；已存在訂單快照金額不變（**FR-012**）。
3. **Given** 管理人員持有僅 **orders** 能力之憑證，**When** 嘗試建立或修改分類／餐點，**Then** 系統回 **403** `MERCHANT_FORBIDDEN`（或等同語意），資料不得變更。
4. **Given** 寫入請求缺少必填欄位或價格非有效十進位格式，**When** 提交建立或更新，**Then** 系統回 **400** 與穩定錯誤碼，不寫入部分資料。

**功能需求（FR）**：

- **FR-001**: 系統必須提供店家專用之餐點分類建立、更新、列表與刪除（或停用）能力；分類名稱在同一店家範圍內不可重複（刪除策略：若仍有餐點引用則拒絕刪除或要求先移轉，實作擇一並在 API 契約中固定）。
- **FR-002**: 系統必須提供店家專用之餐點建立與更新，至少包含 `name`、`price`、`category_id`、可選 `image_url`，以及餐點層級 `is_active` 預設值。
- **FR-003**: 系統必須允許店家維護餐點規格群組與選項（名稱、`price_adjustment`、`is_active`），規則對齊第一迭代讀取模型（每餐點零到多群組、每群組多選項）。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-012、FR-014

### 使用者故事 2 - 店家管理餐點售完與規格停供 (優先順序：P1)

身為具菜單管理權限的店家管理人員，我想將整項餐點或特定規格標為停止供應（售完），並在恢復進貨時重新上架，以便營運當下準確反映可點餐項目。

**為何這個優先順序**：Roadmap **06** 明確列出「餐點售完管理」；第二、三迭代已以 `is_active` 驗證供應狀態，本故事補上店家可操作的持久化開關。

**獨立測試**：將餐點 `is_active=false` 後，顧客菜單顯示停供、無法新增加入購物車；購物車內既有項目標示不可用；建單被拒。將規格選項停供時，僅影響該選項組合。

**驗收情境**：

1. **Given** 一項供應中的餐點，**When** 管理人員將該餐點 `is_active` 設為 false，**Then** 顧客菜單 API 與瀏覽 UI 顯示停止供應；新增加入購物車被拒（**409** `MENU_ITEM_UNAVAILABLE` 或等同語意）。
2. **Given** 購物車內已有該餐點且先前為可用，**When** 管理人員將餐點停供後顧客讀取購物車，**Then** 該列 `availability` 為 `unavailable`，不計入總額，行為對齊第二迭代。
3. **Given** 餐點仍供應中但某一規格選項被停供，**When** 顧客選擇含該選項的組合嘗試加入購物車或建單，**Then** 系統拒絕；未含停供選項之合法組合仍可加入。
4. **Given** 管理人員將已停供餐點恢復 `is_active=true`，**When** 顧客重新載入菜單並選擇合法規格，**Then** 可再次加入購物車並依最新價格計價。

**功能需求（FR）**：

- **FR-004**: 系統必須允許具 menu／admin 權限者更新餐點層級 `is_active`，並立即影響菜單讀取與交易前驗證。
- **FR-005**: 系統必須允許具 menu／admin 權限者更新規格選項層級 `is_active`，並在規格驗證與定價時一併檢查。
- **FR-006**: 系統必須提供專用「供應狀態」更新端點或等價 PATCH 欄位，使店家 UI 可一鍵售完／恢復，無須提交完整餐點表單（若與 FR-002 合併實作，行為須等價）。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-011、FR-013

### 使用者故事 3 - 顧客端反映供應狀態並阻擋無效下單 (優先順序：P1)

身為顧客，我想在瀏覽菜單與購物車中清楚看到停供項目，並在送出訂單時由系統再次確認供應狀態，以便不會誤點已售完餐點或遭前端竄改繞過檢查。

**為何這個優先順序**：整體願景要求「驗證餐點供應狀態」；本迭代在店家可改供應狀態後，須確認顧客路徑端到端一致。

**獨立測試**：停供後檢查 Menu UI 標示、購物車不可用列、建單 **409**；嘗試在請求 body 夾帶 `is_active: true` 或自訂價格，伺服器仍依資料庫拒絕或重算。

**驗收情境**：

1. **Given** 菜單含停供餐點，**When** 顧客瀏覽菜單頁，**Then** 停供餐點有明確「售完／停止供應」標示且無法開啟有效下單流程（或對話框僅允許關閉）。
2. **Given** 購物車含可用與不可用混合項目，**When** 顧客檢視購物車，**Then** 僅可用項目計入總額；不可用項目顯示第二迭代文案，建單按鈕在無可用項目時禁用或拒絕。
3. **Given** 購物車在檢視時全為可用，**When** 送出建單前瞬間餐點被停供，**Then** 建單請求被伺服器拒絕，不產生訂單編號，購物車內容保留。
4. **Given** 建單或購物車 PATCH 請求 body 含自訂 `line_total`、`total_amount` 或 `is_active`，**When** 伺服器處理，**Then** 忽略或可驗欄位不寫入持久化；金額僅依伺服器計算（**FR-012**）。

**功能需求（FR）**：

- **FR-007**: 顧客菜單讀取 API 與前端 MUST 暴露餐點與選項的供應狀態（至少 `is_active` 或衍生 `availability`），停供餐點不得呈現為可正常下單。
- **FR-008**: 建立訂單前 MUST 再次執行與第三迭代相同的整車供應驗證；任一停供即整筆拒絕。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-011、FR-012、FR-013

### 使用者故事 4 - 店家 API 角色權限控管 (優先順序：P1)

身為系統管理者，我想為不同店家人員發放不同能力的憑證（例如僅出餐、僅菜單維護），以便依職責限制可呼叫的 API，取代第四迭代單一 `MERCHANT_TOKEN` 全權模型。

**為何這個優先順序**：Roadmap **06** 明確列出 RBAC；第四、五迭代以單一共用 token 驗證店家訂單 API，本迭代須在不破壞既有部署的前提下分權。

**獨立測試**：設定多組 token／角色；`orders` token 可 list／accept 但不可 PATCH 菜單；`menu` token 可售完但不可 accept；無 token **401**；未設定店家功能 **503** 語意不變。

**驗收情境**：

1. **Given** 環境設定 `MERCHANT_TOKEN`（legacy）或具 **admin** 角色之憑證，**When** 呼叫第四、五迭代任一店家訂單 API 與本迭代菜單寫入 API，**Then** 均可成功（向後相容）。
2. **Given** 憑證僅具 **orders** 角色，**When** 呼叫接單或訂單列表 API，**Then** 成功；呼叫菜單建立／售完 API，**Then** **403** `MERCHANT_FORBIDDEN`。
3. **Given** 憑證僅具 **menu** 角色，**When** 呼叫菜單維護或供應狀態 API，**Then** 成功；呼叫接單或推進出餐，**Then** **403** `MERCHANT_FORBIDDEN`。
4. **Given** 請求未附 `X-Merchant-Token` 或 token 不符，**When** 呼叫任一受保護店家 API，**Then** **401** `MERCHANT_UNAUTHORIZED`；若環境未設定任何有效店家憑證，**Then** **503** `MERCHANT_NOT_CONFIGURED`（與第四迭代一致）。

**功能需求（FR）**：

- **FR-009**: 系統必須支援店家憑證對 **roles** 的映射，至少包含 **`orders`**、**`menu`**、**`admin`**；`admin` 涵蓋 orders 與 menu 全部允許操作。
- **FR-015**: 系統必須延續 **`X-Merchant-Token`** header 作為店家驗證載體；角色資訊由伺服器設定解析，不得由客戶端 header 自報角色繞過。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-014

### 使用者故事 5 - 一致例外處理與錯誤回應 (優先順序：P1)

身為前端或整合測試維護者，我想在所有 API 收到可預期的 JSON 錯誤結構，並在未預期錯誤時仍不洩漏敏感細節，以便統一顯示與記錄問題。

**為何這個優先順序**：Roadmap **06** 列出「例外處理」；第一至五迭代已有多種 `error.code`，本迭代收斂未捕獲例外與回應一致性，支撐整合測試斷言。

**獨立測試**：觸發已知 **400**／**404**／**409** 業務錯誤，body 皆含 `error.code` 與 `message`；模擬路由層未處理錯誤回 **500** `INTERNAL_ERROR` 且無 stack；404 未知路徑回穩定結構。

**驗收情境**：

1. **Given** 請求 body 不符合 schema，**When** 呼叫任一需 JSON body 的 API，**Then** 回 **400** 與 `INVALID_REQUEST_BODY` 或專用驗證碼，不導致未處理例外。
2. **Given** 請求路徑不存在，**When** 呼叫 API，**Then** 回 **404** 與 `NOT_FOUND`（或專用碼），JSON 結構與其他錯誤一致。
3. **Given** 服務層拋出未預期錯誤，**When** 錯誤傳到 Express 錯誤中介層，**Then** 回 **500**、`error.code` 為 `INTERNAL_ERROR`、message 為通用中文；回應 body 不含 stack、SQL 或檔案路徑；詳細資訊僅寫入伺服器日誌（**NFR-010**）。
4. **Given** 業務規則拒絕（如 **409** 狀態衝突），**When** 回應錯誤，**Then** 維持既有穩定 `error.code`（如 `ORDER_STATUS_CONFLICT`），不因本迭代重構而無故更名。

**功能需求（FR）**：

- **FR-016**: 系統必須提供集中式 HTTP 錯誤中介層，將可預期業務錯誤（含 status 與 code）與未預期錯誤分流處理。
- **FR-017**: 系統必須為未知路由提供 JSON **404**  handler，避免 HTML 預設頁面破壞 API 客戶端。

**非功能需求（NFR）**：

- **NFR-011**: 可預期業務錯誤回應時間不應因集中處理而引入額外遠端呼叫；本故事不要求具體毫秒門檻。

**全域需求參照**：NFR-010

### 使用者故事 6 - 整合測試與端到端系統驗證 (優先順序：P1)

身為開發團隊，我想以自動化整合測試覆蓋顧客主路徑、店家操作、售完邊界、防竄改金額與重複送單，以便第六迭代交付時能一次驗證系統正確性。

**為何這個優先順序**：Roadmap **06** 明確列出「整合測試」；前五迭代已有分散單元／HTTP 測試，本迭代補跨模組旅程與回歸護欄。

**獨立測試**：執行 designated 整合測試套件（含 memory DB）：完整旅程 + 竄改 body + 冪等重送 + 停供競態；CI 或 `npm test` 可選子集標記 `@integration` 或獨立檔名約定。

**驗收情境**：

1. **Given** 乾淨測試環境與種子菜單，**When** 執行端到端情境（瀏覽 → 加購物車 → 建單 → 查詢 → 付款 stub 成功 → 店家接單 → 完成），**Then** 各步驟 HTTP 狀態與持久化狀態符合第三至五迭代規格。
2. **Given** 同一建單 `Idempotency-Key`，**When** 整合測試重送建單，**Then** 僅一筆訂單，第二次回 **200** 與相同 `order_number`（第三迭代 **BR-003**）。
3. **Given** 建單或付款請求夾帶竄改之 `total_amount`，**When** 執行整合測試，**Then** 持久化金額仍等於伺服器快照，與第五迭代 **SC-005** 一致。
4. **Given** 整合測試將餐點停供後立即建單，**When** 執行，**Then** 建單失敗且無新訂單；恢復供應後建單成功。
5. **Given** 執行 backend 全 suite，**When** 合併第一至五迭代既有測試，**Then** 全部通過，確保本迭代未破壞回歸。

**功能需求（FR）**：

- **FR-018**: 專案 MUST 提供至少一個可重複執行的整合測試入口（例如 `backend/src/__tests__/integration/` 或 `scripts/smoke-006-*.mjs`），覆蓋 **SC-001** 至 **SC-005** 所描述之跨模組行為。
- **FR-019**: 整合測試 MUST 使用與現有 backend 測試相同的 memory DB／harness 模式，不得依賴手動 UI 操作作為唯一驗收方式。

**非功能需求（NFR）**：

- **NFR-012**: 整合測試套件在預設 CI 環境下 MUST 可完成執行；若執行時間過長，允許與 unit 測試分 job，但 MUST 在 techstack／tasks 中記載執行方式。

**全域需求參照**：FR-011、FR-012、FR-013、NFR-010

### 邊界情況

- 本迭代擴充第四迭代 **`X-Merchant-Token`** 為多憑證 RBAC；既有單一 **`MERCHANT_TOKEN`** 環境變數 MUST 視為 **admin** 全權，以維持既有測試與部署行為。
- 角色設定格式待 **`/technical-research`** 定案（例如 `MERCHANT_CREDENTIALS` JSON 陣列或前綴環境變數）；規格只要求可配置、可測試，不在此鎖死語法。
- 菜單刪除：若規格要求「有訂單快照引用之餐點不可硬刪」，則應提供停用（`is_active=false`）替代；硬刪若允許，不得破壞歷史訂單明細顯示（訂單仍保存 `menu_item_name` 快照）。
- 顧客端點（菜單讀取、購物車、建單、查詢、付款）維持訪客 session 與 CSRF 規則；RBAC 僅適用店家寫入與店家訂單 API。
- 本迭代不包含顧客登入帳號、多店 tenant、真實金流、庫存數量扣減（僅布林供應狀態）、或進階審計日誌 UI。
- 整合測試不含跨瀏覽器 E2E（Playwright）；若需 UI E2E，列為後續或選配，不阻擋 **SC-003** HTTP 整合驗收。
- 價格精度與幣別政策沿用第一至三迭代（十進位字串、`NT$` 顯示）；本迭代不引入多幣別。

## 全域需求 *(僅於存在跨多個 User Story 的需求時納入)*

### 功能需求（FR）

- **FR-010**（適用於使用者故事 1、2、4）: 所有店家菜單寫入 API（分類、餐點、規格、供應狀態）MUST 驗證 `X-Merchant-Token`，且憑證 MUST 具 **menu** 或 **admin** 角色；否則 **403** `MERCHANT_FORBIDDEN`（缺 token 仍為 **401**）。
- **FR-011**（適用於使用者故事 2、3、6）: 加入購物車、更新購物車、建立訂單 MUST 以伺服器讀取之最新 `menu_items.is_active` 與 `menu_item_options.is_active` 驗證供應狀態；客戶端請求中的供應或可用旗標 MUST NOT 作為授權依據。
- **FR-012**（適用於使用者故事 1、3、6）: 購物車與建單金額 MUST 由伺服器依最新菜單價格與規格加價計算；客戶端提交之項目小計、購物車總額或訂單總額 MUST NOT 寫入持久化。已成立訂單查詢 MUST 仍回傳建立時快照（第三迭代 **BR-001**）。
- **FR-013**（適用於使用者故事 2、3、6）: 停供後，既有購物車項目 MUST 標示 `availability: unavailable` 且不計入總額（第二迭代）；新建單 MUST 整筆拒絕直至無不可用項目或顧客移除該列。
- **FR-014**（適用於使用者故事 1、4）: 第四、五迭代店家訂單 API MUST 改為要求 **orders** 或 **admin** 角色；`admin`／legacy **`MERCHANT_TOKEN`** MUST 滿足此要求。

### 非功能需求（NFR）

- **NFR-010**（適用於使用者故事 5、6）: 所有 API 錯誤 JSON 回應 MUST 符合 `{ error: { code, message } }` 結構；**4xx**／**5xx** MUST NOT 在 body 中包含 stack trace、SQL 錯誤原文或伺服器檔案系統路徑。

### 主要實體 *(若功能涉及資料則納入)*

- **餐點分類、餐點、規格群組、規格選項**：在第一迭代模型上新增店家寫入生命週期；`is_active` 表示供應狀態；價格變更影響新購物車計價，不影響舊訂單快照。
- **店家憑證／角色**：設定層映射 token → roles；非持久化實體，不引入顧客帳號表。
- **整合測試情境**：可執行腳本與測試檔，驗證跨 API 不變量，非業務持久化實體。

## 成功標準 *(必要)*

### 可衡量成果

- **SC-001**: 具 menu 權限者可建立分類與餐點，顧客菜單 API 在單次請求內可讀到新資料且欄位正確。
- **SC-002**: 餐點或規格停供後，新增加購物車與建單均被拒絕；既有購物車項目正確標示不可用且不計入總額。
- **SC-003**: 端到端整合測試（HTTP）可完成「加購 → 建單 → 付款 → 店家完成出餐」且狀態與金額正確。
- **SC-004**: 僅 orders 權限憑證無法修改菜單；僅 menu 權限憑證無法接單；admin／legacy token 兩者皆可。
- **SC-005**: 整合測試確認建單／付款 body 竄改總額不改變持久化 `total_amount`。
- **SC-006**: 未處理例外與未知路由均回結構化 JSON 錯誤，且 **500** 回應不含 stack。
- **SC-007**: Backend 全 suite（含本迭代新增整合測試）執行通過，第一至五迭代關鍵測試無回歸失敗。
