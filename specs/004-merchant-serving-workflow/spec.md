# 功能規格：點餐系統第四迭代－店家管理與出餐流程

**功能分支**：`004-merchant-serving-workflow`

**建立日期**：2026-10-14

**狀態**：草稿

**輸入**：使用者描述：「請設計並開發一套完整的點餐系統，提供顧客瀏覽餐點、查看價格、選擇餐點規格與數量、加入購物車、確認訂單及查詢訂單狀態等功能，並提供店家管理介面，讓管理人員可以維護餐點分類、餐點資訊、價格、供應狀態及訂單資料。系統需具備訂單金額計算、訂單狀態管理、付款狀態管理及訂單紀錄查詢等功能，並確保資料正確性、避免重複送單、驗證餐點供應狀態及防止前端竄改訂單金額。此需求分成 6 次迭代開發；請先開發 04 項目。04：店家管理與出餐流程，店家可以接受訂單、更新出餐狀態、完成訂單。」

## 商業規則 *(必要)*

- **BR-001**: 訂單明細與訂單總金額在顧客建立當下已快照持久化；店家出餐流程僅能變更訂單狀態及狀態相關時間戳，不得修改明細、數量、單價、項目金額或訂單總金額，亦不得採信店家端提交的金額欄位覆寫持久化資料。（對應需求：**FR-012**、**FR-013**）
- **BR-002**: 訂單狀態僅能依本迭代定義的狀態機前進；不得由「已完成」退回較早狀態，亦不得跳過必要的中間狀態（「已建立」→「已接單」→「出餐中」→「已完成」）。（對應需求：**FR-006**、**FR-007**、**FR-008**、**FR-009**）
- **BR-003**: 同一筆訂單在任意時刻僅有一個有效的持久化訂單狀態；顧客查詢與店家檢視須讀取同一持久化狀態，不得各自維護不一致的狀態副本。（對應需求：**FR-011**）

## 使用者情境與測試 *(必要)*

### 使用者故事 1 - 店家檢視訂單佇列與明細 (優先順序：P1)

身為店家管理人員，我想在管理介面中檢視待處理與進行中的訂單列表及單筆訂單明細，以便依建立時間與狀態安排出餐。

**為何這個優先順序**：沒有可讀的訂單佇列，店家無法得知哪些訂單待接單或製作中；這是接單與出餐動作的前置條件。

**獨立測試**：建立多筆不同狀態的訂單後，以有效店家憑證開啟管理介面或呼叫店家訂單 API；確認列表含訂單編號、狀態、建立時間、總金額，且明細與第三迭代快照一致。未帶憑證時應拒絕存取。

**驗收情境**：

1. **Given** 系統存在至少一筆狀態為「已建立」的訂單，且管理人員持有有效店家憑證，**When** 管理人員開啟訂單列表，**Then** 列表顯示該訂單的訂單編號、狀態「已建立」、建立時間及訂單總金額快照，且可依狀態或時間排序／篩選（至少支援依狀態篩選「已建立」）。
2. **Given** 管理人員持有有效店家憑證，**When** 管理人員檢視某一筆訂單的詳情，**Then** 系統顯示該訂單的訂單編號、目前狀態、建立時間、訂單總金額快照，以及各明細的餐點名稱、規格摘要、數量、單價與項目金額快照。
3. **Given** 請求未附有效店家憑證或憑證無效，**When** 呼叫店家訂單列表或詳情 API，**Then** 系統拒絕存取，不揭露訂單內容。
4. **Given** 訂單建立後菜單價格已變更，**When** 管理人員檢視該訂單詳情，**Then** 顯示的金額仍為建立當下快照，而非最新菜單價格。

**功能需求（FR）**：

- **FR-001**: 系統必須提供店家專用的訂單列表，列出持久化訂單的訂單編號、訂單狀態、建立時間及訂單總金額快照。
- **FR-002**: 系統必須允許持有有效店家憑證的管理人員，依訂單編號或內部識別檢視單筆訂單詳情，含明細快照（餐點顯示名稱、規格摘要、數量、單價、項目金額）及訂單總金額快照。
- **FR-003**: 系統必須支援店家訂單列表至少依訂單狀態篩選，以便優先處理「已建立」待接單訂單。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-011、FR-012

### 使用者故事 2 - 店家接受訂單 (優先順序：P1)

身為店家管理人員，我想將顧客新送出的訂單標記為已接單，以便開始出餐並讓顧客得知訂單已被受理。

**為何這個優先順序**：接單是出餐流程的起點；第四迭代明確交付「店家可以接受訂單」。

**獨立測試**：對狀態為「已建立」的訂單執行接單操作；確認持久化狀態變為「已接單」且非法狀態或重複接單被拒絕。

**驗收情境**：

1. **Given** 一筆訂單目前狀態為「已建立」，且管理人員持有有效店家憑證，**When** 管理人員對該訂單執行接單，**Then** 訂單狀態更新為「已接單」，並記錄狀態更新時間；回應與詳情查詢均顯示新狀態。
2. **Given** 一筆訂單狀態已為「已接單」、「出餐中」或「已完成」，**When** 管理人員嘗試再次執行接單，**Then** 系統拒絕操作，訂單狀態維持不變。
3. **Given** 接單請求未附有效店家憑證，**When** 管理人員嘗試接單，**Then** 系統拒絕操作，訂單狀態不得變更。
4. **Given** 接單請求 body 夾帶自訂訂單總金額或明細金額，**When** 系統處理接單，**Then** 僅更新允許的狀態欄位，持久化金額與明細不受請求 body 影響。

**功能需求（FR）**：

- **FR-004**: 系統必須允許持有有效店家憑證的管理人員，將狀態為「已建立」的訂單轉換為「已接單」。
- **FR-005**: 系統必須在接單成功時持久化新狀態及狀態更新時間。
- **FR-006**: 系統必須拒絕對非「已建立」狀態訂單執行接單。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-011、FR-012、FR-013

### 使用者故事 3 - 店家更新出餐狀態並完成訂單 (優先順序：P1)

身為店家管理人員，我想將已接單的訂單標記為出餐中，並在完成備餐後標記為已完成，以便追蹤出餐進度並結束該筆訂單的廚房流程。

**為何這個優先順序**：第四迭代明確交付「更新出餐狀態、完成訂單」；與接單共同構成完整出餐狀態管理。

**獨立測試**：依序對「已接單」訂單標記出餐中、再標記已完成；驗證非法跳步或逆向轉換均被拒絕。

**驗收情境**：

1. **Given** 一筆訂單目前狀態為「已接單」，且管理人員持有有效店家憑證，**When** 管理人員將該訂單更新為「出餐中」，**Then** 訂單狀態持久化為「出餐中」，並記錄狀態更新時間。
2. **Given** 一筆訂單目前狀態為「出餐中」，**When** 管理人員將該訂單標記為「已完成」，**Then** 訂單狀態持久化為「已完成」，並記錄狀態更新時間。
3. **Given** 一筆訂單狀態為「已建立」，**When** 管理人員嘗試直接更新為「出餐中」或「已完成」，**Then** 系統拒絕操作，狀態維持「已建立」。
4. **Given** 一筆訂單狀態為「已完成」，**When** 管理人員嘗試更新為「出餐中」或「已接單」，**Then** 系統拒絕操作，狀態維持「已完成」。
5. **Given** 狀態更新請求未附有效店家憑證，**When** 管理人員嘗試更新出餐狀態或完成訂單，**Then** 系統拒絕操作，訂單狀態不得變更。

**功能需求（FR）**：

- **FR-007**: 系統必須允許持有有效店家憑證的管理人員，將「已接單」訂單轉換為「出餐中」。
- **FR-008**: 系統必須允許持有有效店家憑證的管理人員，將「出餐中」訂單轉換為「已完成」。
- **FR-009**: 系統必須拒絕不符合狀態機的轉換（含跳過「已接單」或「出餐中」、以及由「已完成」退回）。
- **FR-015**: 系統必須在每次成功的狀態轉換時持久化新狀態及狀態更新時間。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-010、FR-011、FR-012、FR-013

### 使用者故事 4 - 顧客查詢反映店家更新後的訂單狀態 (優先順序：P1)

身為曾建立訂單的顧客，我想在查詢訂單時看到店家接單與出餐進度更新後的最新狀態，以便了解訂單目前進度。

**為何這個優先順序**：第三迭代已提供顧客查詢；若狀態更新不同步，出餐流程對顧客不可見，訂單狀態管理的價值無法驗收。

**獨立測試**：顧客建立訂單後，店家依序接單、標記出餐中、完成；顧客以同一訪客工作階段與訂單編號查詢，確認 `status`／`status_label` 與店家操作後一致。

**驗收情境**：

1. **Given** 顧客於有效訪客工作階段建立一筆訂單且狀態為「已建立」，且店家已將該訂單接單，**When** 顧客以該訂單編號查詢訂單，**Then** 回應的訂單狀態為「已接單」（對應 API 列舉與中文標籤）。
2. **Given** 店家已將訂單標記為「出餐中」或「已完成」，**When** 建立該訂單的同一訪客工作階段查詢該訂單，**Then** 回應狀態與持久化結果一致，明細與快照金額仍與建立時相同。
3. **Given** 訂單狀態已為「已完成」，**When** 顧客查詢該訂單，**Then** 回應包含狀態「已完成」，且不暴露其他訪客工作階段的訂單。

**功能需求（FR）**：

- **FR-014**: 系統必須在顧客依第三迭代規則查詢訂單時，回傳目前持久化的訂單狀態（含 API 列舉值與顯示用中文標籤），而非固定僅「已建立」。

**非功能需求（NFR）**：本故事未明確提出專屬 NFR。

**全域需求參照**：FR-011

### 邊界情況

- 店家訂單 API 與管理介面須與顧客端隔離：顧客訪客工作階段不得用於接單或更新出餐狀態；店家憑證不得用於代替顧客查詢他人訂單（除非另有店家專用查詢端點）。
- 本迭代訂單狀態列舉為 **`created`（已建立）→ `accepted`（已接單）→ `preparing`（出餐中）→ `completed`（已完成）**；不提供拒單、取消、作廢或付款相關狀態（屬第五迭代）。
- 對不存在或無效的訂單編號執行接單或狀態更新時，回傳查無或等同拒絕，且不洩漏其他訂單是否存在。
- 並發狀態更新：伺服器以持久化當下狀態驗證轉換（條件 `UPDATE`）；若來源狀態與資料庫不一致或並發競態，回 **409** `ORDER_STATUS_CONFLICT`，維持現狀（客戶端可重新讀取後重試）。
- 狀態轉換須透過固定 **POST 動作**（接單、開始出餐、完成訂單）逐步持久化；不得接受店家自填任意目標狀態字串。UI 可合併按鈕，但伺服器仍須依序寫入狀態。
- 店家列表 `GET` 支援 `status` 查詢參數篩選；非法值回 **400** `INVALID_STATUS_FILTER`。預設依建立時間降序；首版列表上限 **200** 筆（無分頁）。
- 店家 API 不使用訪客 CSRF；`MERCHANT_TOKEN` 未設定時店家端點回 **503** `MERCHANT_NOT_CONFIGURED`。
- 本迭代不提供餐點分類、餐點資訊、價格或供應狀態的維護介面（整體產品願景中的「維護餐點資料」歸第六迭代進階能力或其他未在本迭代定義的交付）；店家介面聚焦訂單檢視與出餐狀態操作。
- 付款狀態欄位、金流結果與訂單取消規則不在本迭代範圍；完成訂單僅表示廚房／出餐流程結束，不代表已收款。

## 全域需求 *(僅於存在跨多個 User Story 的需求時納入)*

### 功能需求（FR）

- **FR-010**（適用於使用者故事 1、2、3）: 店家訂單列表、詳情、接單及狀態更新必須經 **`X-Merchant-Token` HTTP header** 與伺服器環境變數 **`MERCHANT_TOKEN`** 常數時間比對；缺漏、不符或未設定（伺服器無 `MERCHANT_TOKEN`）分別回 **401** `MERCHANT_UNAUTHORIZED` 或 **503** `MERCHANT_NOT_CONFIGURED`，不得讀取或變更訂單資料。店家路由不得採用訪客 `guest_session` 或 CSRF。本迭代不提供多角色帳號、密碼重設或權限分級；未來若改 JWT／OAuth 須另開 spec 修訂。
- **FR-011**（適用於使用者故事 1、2、3、4）: 訂單狀態以伺服器持久化為唯一權威；店家操作成功後，顧客查詢與店家檢視須回傳相同狀態列舉值與對應中文標籤。
- **FR-012**（適用於使用者故事 1、2、3）: 店家檢視與狀態更新流程不得修改訂單明細內容、數量或任何快照金額欄位。
- **FR-013**（適用於使用者故事 2、3）: 店家狀態更新請求 body 中若有訂單總金額、項目金額、單價或明細結構欄位，伺服器不得採信或寫入；僅處理允許的狀態轉換語意。

### 主要實體 *(若功能涉及資料則納入)*

- **訂單**：沿用第三迭代；本迭代擴充可變更的 `status` 及狀態更新時間（如 `status_updated_at`），明細與總金額快照維持建立時不變。
- **訂單狀態**：有限狀態機上的列舉值；對外 API 同時提供機器可讀列舉與中文 `status_label`。
- **店家憑證**：部署設定的共享秘密；管理介面以 header **`X-Merchant-Token`** 傳遞，開發環境可經 **`VITE_MERCHANT_TOKEN`** 注入前端；與顧客訪客工作階段分離。

## 成功標準 *(必要)*

### 可衡量成果

- **SC-001**: 持有有效店家憑證時，可列出含「已建立」訂單的佇列，且單筆詳情的明細與金額與訂單建立快照一致。
- **SC-002**: 「已建立」訂單經接單後，持久化狀態為「已接單」；對非「已建立」訂單接單均被拒絕且狀態不變。
- **SC-003**: 「已接單」→「出餐中」→「已完成」的合法序列可成功執行；跳步、逆向或非法狀態轉換均被拒絕。
- **SC-004**: 店家每次成功狀態轉換後，建立該訂單的顧客以原訪客工作階段查詢時，回傳與店家側一致的最新 `status`／`status_label`，且快照金額不變。
- **SC-005**: 未附或附無效店家憑證的店家 API 請求無法讀取訂單列表或變更訂單狀態。
- **SC-006**: 任一店家狀態操作均不變更訂單明細或訂單總金額快照。

## 假設

- 第一至第三迭代已提供餐點瀏覽、購物車、訂單建立與顧客查詢；訂單初始狀態為 `created`／「已建立」，訂單編號與快照語意沿用第三迭代。
- 本迭代範圍對齊 roadmap **04「店家管理與出餐流程」**：訂單檢視、接單、出餐狀態更新、完成訂單；**不包含**餐點分類／餐點 CRUD／價格維護（整體願景中的店家資料維護留待後續迭代，例如第六迭代進階功能）。
- 店家憑證與狀態轉換 POST 動作之技術細節與 [research.md](./research.md)「店家憑證驗證」「訂單狀態機與並發安全」決策一致；OpenAPI 契約見 `contracts/http-api.yaml`。
- 本迭代不提供訂單拒絕、取消、退款或付款狀態更新（第五迭代）；「已完成」不表示付款成功。

## 澄清紀錄

### Session 2026-10-14（clarify-over-specs · 對齊 research）

- Q1: 店家憑證驗證機制是否定案？ → A: **`X-Merchant-Token` header** 對 **`MERCHANT_TOKEN`**；401／503 語意同 research；店家 API 不用 CSRF／guest session。
- Q2: 狀態轉換是否允許任意 target status？ → A: **否**；僅 **accept／start-preparing／complete** 三 POST 動作，狀態機 `created→accepted→preparing→completed`；並發／非法轉換 **409** `ORDER_STATUS_CONFLICT`。
- Q3: 列表篩選與上限？ → A: 可選 **`status` query**；非法值 **400** `INVALID_STATUS_FILTER`；首版最多 **200** 筆、依 `created_at` DESC。
